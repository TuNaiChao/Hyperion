# Hyperion 设计思路转变史

> 本文档专门记录本项目开发中**所有重大设计思路的转变**:从 X 改到 Y、为什么、依据、关联。
> 与 [踩坑记录.md](踩坑记录.md) 互补:踩坑 = 走过的弯路(反面教材,五段式 现象→弯路→根因→教训→现状);本文件 = **决策演变脉络**(中性,从→到 + 为什么)。
> **设计前先查这里**,理解"为什么现在是这个设计";新转变往上加(阶段递增)。

---

## 阶段 0:v0 → v2 重规划(2026-07-28)

- **从**:"先建深地基(代码情报/记忆/沙箱全套),再接场景"。
- **到**:"编排 + 记忆 + 委托"——先做 MVP 场景(bug-RCA),地基按需建。
- **为什么**:先建全套地基 = 长期不见产出 + 容易过度设计;改场景驱动。
- **依据**:用户重规划;详见 [CLAUDE.md](CLAUDE.md) 路线 v2 段。

## 阶段 1:三锁定决策(2026-07-28,基石,别推翻)

1. **记忆**:**从** cognee/mem0 **到** 自建 `MemoryService`(native:SQLite+FTS5+向量)。
   - 为什么:自有契约可控 + 组合 code_index/code-review-graph;cognee/mem0 可换、v1 不用。
2. **bug-RCA 重活**:**从** Hyperion 自跑 **到** 委托 coding agent(opencode)。
   - 为什么:opencode 是强 coding agent,定位/改码是它强项;Hyperion 不 double-localize(→ 踩坑 #2)。
3. **MVP**:**从** 三支柱齐头 **到** 先 bug-RCA(P2)。
   - 为什么:bug-RCA 价值最直接 + 验证记忆/代码情报/委托全栈。

## 阶段 2:R2-R3 的几次反转(2026-07 ~ 08)

- **patch 多候选投票 rerank**:**当主路径 → 降级默认关 → 整体移除**(踩坑 #1)。
  - 为什么:wpa/bluez 无测试套件 + glm 近确定性 → 投票平凡 + 白烧 token;现代 SOTA 转单轨迹+执行验证。改**迭代 verify-refine**。
- **Hyperion 侧定位漏斗**:**建到一半砍掉**(踩坑 #2)。
  - 为什么:Agentless 式漏斗与 opencode 重复定位(double localization);改"opencode 自定位 + Hyperion 把记忆/检索/日志过滤做成 MCP 工具给它调"。**这条是阶段 3 转向的前奏**。
- **runtime 中间件**:**从** 抄 deer-flow 30+ **到** pull-by-need 加([[runtime-middleware-policy]])。
  - 为什么:YAGNI;扩展口已留(middleware 列表 + state_schema 自动合并),按需加,不预塞。
- **记忆写入语义**:**从** 覆盖式 supersede **到** 只追加 + 检索时最新为主(2026-08-06,[[memory-append-only-directive]])。
  - 为什么:对标 mem0 v3(arXiv:2504.19413);写入时消歧→检索时推理,失真风险更低。

## 阶段 3:Harness 转向(2026-08-06,最大的一次)

- **从**:Hyperion 当 **orchestrator**(卡 opencode 走固定六节点管线定位 bug)。
- **到**:**tool+skill server / 领域 harness**(bug-RCA 主路径 = opencode + bug-rca skill + hyperion MCP 工具,agent 自驱;orchestrator 降级留参考)。
- **为什么**:① orchestrator 跟 opencode 在代码推理上竞争(必输);② 固定图压开放问题(bug 根因路径不可预知)→ 脆弱(踩坑 #7/#8/#9 recursion/死锁/keying)+ 产次优补丁;③ 价值其实在记忆/代码情报/日志/验证/方法论,打包成 agent-agnostic 的 tool+skill 反而增值。
- **依据**:Anthropic "Don't Build Agents, Build Skills Instead" + code-review-graph/Sourcegraph 都是 tool-server(PROVIDER 不 DRIVER) + 踩坑 #2 项目级泛化 + MCP 是 2026 给 coding agent 暴露能力的共识。
- **产物**:D0 MCP 双 transport(stdio + streamable-http)+ 4 新工具(blast_radius/validate_patch/export_patch/export_report)+ bug-rca SKILL.md + hyperion-bug-rca agent。详见 [[harness-pivot-handoff]]。

## 阶段 4:post-pivot 演化(2026-08-06 ~ 08-07)

- **落盘交付门**:**从** "agent 只 edit 代码 + 聊天回复报告" **到** 补丁/报告**落盘硬门**(export_patch + export_report)。
  - 为什么:聊天回复不算交付;`.patch`/`-rca.md` 才是给人/CI/归档的产物。
- **bug-RCA skill 范式**:**从** 固定流水线(9 步 4 硬门,单 session 一次走完)**到** 工具箱 + 人在环迭代(踩坑 #11/#12)。
  - 为什么:① glm-5.2 连续 4 次误诊(e2e#2/#4/#5,踩坑 #11)—— LLM 确认偏差,soft 指令纠不过;② 补丁 plausible 非金标 + apply 过 ≠ 修对(踩坑 #12)—— 自动验证不够,真机是 oracle。改迭代(假设↔证伪 / 补丁↔验证循环)+ memorize/report 验证后才做。
  - 依据:Anthropic toolbox vs fixed pipeline + POPPER ICML2025 迭代证伪 + RepairAgent ICSE2025 补丁-验证循环 + METR 自动验证不够。详见 [[bug-rca-skill-toolbox-hitl]]。
- **skill/prompt 写法**:**从** 面向小白/项目叙事 **到** 面向模型指令性(踩坑 #13)。
  - 为什么:skill/prompt 受众是模型,项目内部知识(踩坑编号/误诊史/e2e/对标论文/日期)+ 教学口吻是噪声。改指令性、去叙事;项目知识留 docs/踩坑 + memory。
  - 依据:Anthropic Agent Skills 最佳实践(write for model not human + progressive disclosure)。详见 [[skill-prompt-writing-style]]。
- **filter_logs 边界提醒(方案 A)**:**从** 被动执行 agent 的(可能错的)时间窗 **到** 切窗 + 确定性边界提醒(踩坑 #11)。
  - 为什么:e2e#5 agent 从 abort 时刻切窗,漏 7 秒前真起因 → RCA 走偏;模型确认偏差改不了,但工具能在输出里强制提醒"窗前可能有起因"。

### P-A 1a(补丁/PR 鉴定,2026-08-07)

- **形态**:**从** pre-pivot 的 workflow(pr-review-design.md)**到** tool+skill(patch-review skill + hyperion-patch-review agent + 共享/新 MCP 工具),跟 bug-RCA 一致;不建 workflow(批量 1b 才走 batch 形)。
  - 为什么:harness 转向的延续(踩坑 #2:委托型别重造管线;Anthropic toolbox)。
- **build_check 接入又退出**:**从** "Tier 0.5 编译门(apply+build 封顶)"**到** "退出流程,只到 apply,编译由用户自验"(踩坑 #14)。
  - 为什么:系统软件构建前置重(git 标签/.config/依赖),本机缺 → baseline 本就 build 不了 → `builds=no` 不归咎补丁,信号歧义。build_check 工具保留(按需/可逆),R5 Docker 环境就绪再接回。
- **memorize 时点对齐 bug-rca**:**从** "鉴定完成即 memorize"**到** "用户验证(编译/真机)通过后才 memorize"(踩坑 #12 同源)。
  - 为什么:鉴定只是读码判断(没编译没测试),未验证就 memorize = 把没坐实的结论当教训污染记忆。bug-rca 早立了"验证后才 memorize",patch-review 起初没对齐,e2e 暴露(apply 失败下仍 memorize)→ 改齐。
- **只读 skill 权限收紧**:**从** patch-review `edit:deny + bash:allow`**到** `edit:deny + bash:deny`(踩坑 #16)。
  - 为什么:bash 能 `git apply`/`checkout` 改文件,绕过 edit:deny;e2e 里 agent 偷偷把补丁贴进了 demo 仓。只读鉴定 skill 不该有改用户仓的能力 → bash:deny。bug-rca 才需要 bash(它改代码)。
- **工具入口容错 agent 传参**:**从** 假设 agent verbatim 传补丁 **到** 工具入口 normalize(LF + 补末尾换行)(踩坑 #15)。
  - 为什么:agent(弱模型)读/传时常 rstrip 末尾换行 → git apply "补丁损坏"误判。接收 agent 字符串的工具必须容错 marshalling。
- **改名 patch-rca → patch-review**:**从** `patch-rca` **到** `patch-review`。
  - 为什么:rca = root cause analysis(找根因,bug-rca 干的);补丁鉴定是 review/assess,不是找根因。两个 skill 都叫 `*-rca` 易混。
  - 详见 [[p-a-1a-handoff]]。

## 持续有效的原则(未反转,贯穿各阶段)

- **委托型 agent 不建平行管线**(踩坑 #2 教训,阶段 2 确立,阶段 3 转向强化):opencode 会的别重造,做 MCP 工具给它调。
- **设计前先调研前沿 + 参考 deer-flow**(⭐ 工作准则):WebSearch 2025-2026 + 精读 deer-flow 对应模块。
- **验证封顶**:apply/build 过 = plausible,非最优;系统软件真机是 oracle(踩坑 #11/#12)。
- **代码注释面向小白;skill/prompt 面向模型**(踩坑 #13,两受众别混)。
- **没核前提别动手**(通病,踩坑 #1/#2/#5/#7/#11/#12):设计前先问"前提成立吗?(有 oracle 吗?opencode 会不会?自动验证够吗?能一次到位吗?)"。
