# Go 工程要点( Multica server 侧 )

> 源码锚点 `v0.4.31-2-g8c9b7503a`;file:line 相对 `multica/server/`。定位:一份「同规模 Go 后端怎么做」
> 的参照样本 —— 1442 个 .go(806 个测试)、376 个迁移、单模块同时装云 server 与设备 daemon。

## 一、模块与依赖选型

- 单 Go 模块 `github.com/multica-ai/multica/server`(go 1.26.6),cmd/{server,multica,migrate} + 三个
  backfill 工具;`internal/`(领域)+ `pkg/`(可外部复用的叶子)。
- 选型全「标准件」:路由 **chi v5**(不用 gin/echo)、DB **pgx/v5 + pgxpool + sqlc**(不用 ORM)、
  websocket **gorilla**、CLI **cobra**、日志 **lmittmann/tint**(彩色的 slog)、调度 **robfig/cron**、
  ID **自铸 UUIDv7**(pkg/dbid)+ oklog/ulid 只给 relay/事件 id、观测 **prometheus**、配置解析
  go-toml/shellwords、LLM 辅助层 openai-go、通知 resend-go、集成 slack-go。无 grpc、无 kafka —— WS +
  REST + Redis Streams 撑住全部通信。
- 一个值得注意的自律:**openai SDK 只有 pkg/llm 一个包允许 import,且有测试断言锁死**(client.go:1-72);
  未配置时零上游请求(ErrNotConfigured)。LLM 只做 chat 起标题/快捷回复,**不在 agent 执行路径上**。

## 二、分层纪律

`cmd/*`(只做装配/监听器)→ `internal/handler`(HTTP,343 文件)→ `internal/service`(领域)→
`pkg/db/generated`(sqlc)→ 叶子 `pkg/*`(protocol/dispatch/dbid/featureflag/llm/plugincontract/
redact/taskfailure)。dispatch 被刻意做成叶子包并写明动机:「handler 和 service 引用的拒绝词表永不
漂移」(dispatch/reason.go:1-12)。

## 三、注释即设计文档(最值得学的一点)

几乎每条非显然不变量都带 MUL-xxxx / #nnnn 工单注释解释**为什么**:

- 停机顺序为什么是这个序(cmd/server/main.go:690-706);
- 「WS 提示 advisory、HTTP claim 是 source of truth」(daemonws/hub.go:185-186);
- 「slot-before-claim:领到的任务必有本地容量」(daemon.go:4711-4715);
- runtime_offline / runtime_unusable / agent_runtime_required 三词分立的原因(dispatch/reason.go:33-49);
- HOME/XDG 为什么不动(daemon.go:7046-7053,MUL-5578);
- Landlock 为什么不用(execenv/codex_sandbox.go:64-79)。

对比本项目(RootRecall)踩坑记录的教训「菜谱沉默处 = 自由裁量处」—— Multica 用工单号把裁量处钉死,
且能反查到事故上下文,是同一纪律的工程化形态。

## 四、优雅停机编排(cmd/server/main.go:679-752)

可选停机保持窗(`MULTICA_SHUTDOWN_HOLD_DURATION` 供排障,:219-239)→ `signal.Stop`(第二信号直接杀)
→ 分层排水:HTTP → 巡检/心跳批处理器 → webhook/telegram worker → 频道 supervisor(有界等待,租约 TTL
兜底)。daemon 侧自更新带 claim 屏障,更新永不与任务领取竞速(daemon.go:4524-4580)。

## 五、依赖注入与并发

- 构造器注入窄接口:`service.TaskWakeupNotifier`、`realtime.Broadcaster`、`daemonws.HeartbeatHandler/
  RPCHandler`(DB 依赖就绪后再回填,hub.go:222-258);测试全用假件(daemon.go:172-179 taskRunner 接口)。
- `golang.org/x/sync` 用得克制:errgroup 做有界扇出(skill 上传 handler/skill.go:1399)、singleflight
  做冷缓存去重(integrations/ghsnapshot/client.go:74);取消语义要紧处自写信号量。
- claim 的「WS RPC 结果未知不得 HTTP 兜底重领」防双领窗口(wsrpc.go:22-32, 350-364)、SQL 层
  `FOR UPDATE SKIP LOCKED` + prepare 租约(agent.sql:722-876)—— 分布式正确性细节处理得相当扎实。

## 六、观测与运维

- metrics 单独 loopback server + 独立小 pgxpool —— 抓取卡死不饿业务连接(main.go:478-523);pprof
  常开(:557, 664-669)。
- 请求日志带慢请求归因,daemon 鉴权路径打标签(middleware/daemon_auth.go:25-51)。
- 迁移器 `cmd/migrate` 自带并发/冗余索引/重试测试;down migration 一等公民(`make migrate-down`)。

## 七、构建与 self-host

- Makefile:`make build` 用 ldflags 把 version/commit/date 铸进 `server/bin/{server,multica,migrate}`;
  `make sqlc` 钉 sqlc v1.31.1;`make test` 先跑迁移再 race 模式全测;worktree 感知的 env 文件切换
  (`.env` vs `.env.worktree`,:3-5, 222-256)。
- self-host = compose 三件套(pgvector:pg17 + backend + frontend)+ Makefile 自动生成秘密 +
  `multica setup self-host` 引导(CLI_AND_DAEMON.md:391-416)。
- 单二进制 CLI+daemon:`multica daemon start` fork 自身;internal/selfexec 50 行解决 os.Executable 失败
  时的自我定位(selfexec.go:12-50);同一二进制还会 re-exec 自己当 execenv 准备助手(cmd/multica/
  main.go:100-107)。

## 八、对 RootRecall 的可借鉴点(按性价比排序)

1. **工单号注释纪律**(§三):RootRecall 的 SKILL/代码注释可引入轻量等价物 —— 每条「为什么这样做」
   挂踩坑号或 e2e 日期,让未来读者能反查事故。已有雏形(踩坑#N 引用),差在 src 层没铺开。
2. **UUIDv7 为主键保 B-tree 局部性**(pkg/dbid):若 RootRecall 记忆库未来迁 sqlite→PG 或加任务表,
   直接抄这个决策(应用层铸造、明确不用作密钥)。
3. **能力头协商代替版本号比较**(local-worktree-v1):比 `MinLocalWorktreeCLIVersion` 这种展示性版本
   闸可靠得多 —— RootRecall 的 CLI/daemon 版本地基(quickstart/wire 脚本)如有跨版本兼容需求,能力集
   合比版本号比对健壮。
4. **fail-closed 优于截断**:未跟踪文件回放超限直接失败并给可操作错误(03 §四)、输出流无终止信号按
   失败(02 §2)—— 与本项目「静默截断 = 撒谎」(#19)完全同源,可引用为外部佐证。
5. **辅助 LLM 层的隔离模式**:单一包持有 SDK + 未配置零请求 + 测试锁死 import —— RootRecall 若将来加
   LLM 辅助(如记忆自动去重摘要),照这个模式圈住。
6. **metrics 独立连接池**:小而实用,防观测面拖垮业务面。
