# 踩坑记录(Pitfall Log)

> 本文档专门记录 Hyperion 项目设计/实现中走过的**弯路**、踩过的**坑**,以及背后的**根因**和**教训**。
> 每条 = 一个坑,固定五段:**现象 → 弯路走了哪几步 → 根因 → 教训(可迁移)→ 现状**。
>
> **目的**:把"反应式打补丁"变成"前置认知",避免重复踩同一个坑。新坑往上加(序号递增)。
>
> **写入时机**:做了设计反转 / 删了已建的代码 / 用户指出过度设计 / 调研推翻既有方案 / 踩了库或模型的非显然坑 时。
>
> 配套:具体设计真相看 `docs/设计/`;决策记忆看 `.claude/memory/`。本文是"**为什么这么决策**的反面教材汇总"。

## 坑 #1:patch 投票 rerank —— 一次三段反转的弯路(2026-07)

### 现象(一句话)
为 bug-RCA 设计了 Agentless 式「多候选补丁 + majority voting」rerank 机制,经历 **当主路径 → 降级为默认关兜底 → 整体移除** 三步反转,最终全删。净效果:白建了一整套(`rerank.py` + config + state + test + 三处复用规划 A/B/C),又全拆掉。

### 弯路走了哪几步(三次认知更新)
1. **初版(当成主路径)**:照搬 Agentless「②repair 采 N 候选 → ③verify 选 top-1(majority voting)」,甚至提前排了 **A/B/C 三处复用**(A=localize 文件投票 / B=深度调研事实一致性 / C=有 oracle 的 patch),觉得这套「采 N 个 → 归一化 → 投票」原语很值钱,得多处复用才回本。
2. **第一次反转(#54-rework → B,2026-07-30)**:意识到 wpa/bluez **无测试套件** + glm-5.2 **近确定性** → N 个补丁几乎一样 → 投票平凡 + N× token 白烧。主路径改**迭代 verify-refine(B)**(同 opencode 会话双循环 + verdict 自审 + `validate_patch` 执行门控),rerank "降级为默认关的兜底"。
3. **第二次反转(整体移除,2026-07-31)**:连"默认关兜底"也删了。导火索是准备上 **localize 文件投票(A)** 时,用户质疑"这是不是过度设计 / 白烧 token"。深度调研(OpenHands/Aider/R2E-Gym/Agentless 原文)坐实:① 投票只在有 oracle 时有效;② 现代 SOTA 已转单轨迹+执行验证。→ `rerank.py` 整文件 + `_rerank_fallback` + `RerankConfig` + `delegate.rerank` + state 两字段 + 测试,全删。

### 根因(为什么是坑)
- **投票有效的前提没在设计前就想清楚**:它有效需(二选一)① 廉价可靠 **oracle**(测试/repro);② 样本**多样 + 可归一化到同一规范解**(self-consistency)。**Agentless 投票原文就是 "majority voting after test filtering"** —— filter+vote 的命门是测试当裁判。wpa/bluez 既无测试、模型又近确定性,**两条都不沾 → 投票必然平凡**。这个前提本该在动手写 `rerank.py` 前就问清楚。
- **"默认关兜底"是伪安全**:留一个永不开启的开关,既增加 config/state/test/文档的维护面,又给架构故事添噪(读者要问"这开关啥时候开?"),还不提供真实逃生口(没 oracle 时开了也没用)。**死代码不是保险,是债。**
- **没跟上趋势**:2025-2026 SOTA —— OpenHands(critic 模型 + 执行反馈)、Aider(单轨迹 + lint/test 每步)、R2E-Gym(执行式验证 > 无执行)—— **已弃文本相似度投票**,转单轨迹 + 执行信号验证。我们的 B verify-refine 正是这条路,rerank 是逆趋势的遗留。
- **"原语值钱得多处复用"的执念**:为分摊设计成本,提前规划 A/B/C 三处复用,反而让一个该删的东西显得"动不得"。复用是结果,不是理由。

### 教训(可迁移到别的坑)
1. **上多采样/投票前先问两个问题**:「这有 oracle 吗?样本会真多样吗?」两否 → 别上,走迭代 refine。没有裁判的投票是安慰剂。
2. **别留"默认关"的死代码兜底** —— 要么它有用(默认开),要么删。YAGNI:不为投机未来扛死代码。真到那天,算法 ~40 行、git 史可查,重写比维护一个语义模糊的开关便宜。
3. **区分两个 "rerank",别误伤**:① patch **多数投票**(Agentless 式,本坑,已删);② **检索 cross-encoder 重排**(BM25→精排召回块,标准 IR 技术,默认开、有效)。砍 (a) 时差点因为名字一样误伤 (b)。
4. **用户对复杂度的直觉通常对** —— 当用户说"这是不是过度设计",往往是。该认真调研验证,而不是为已有代码辩护。
5. **设计前先查前提条件**(本仓有没有测试套件?模型确不确定?),别等建完了跑不通才发现前提不成立。

### 现状(2026-07-31 定稿)
- **全删**:`rerank.py`(整文件)、`nodes._rerank_fallback`、`RerankConfig` + `delegate.rerank` 配置、state `candidates`/`rerank_summary`、rerank fallback 测试。ruff 全过、pytest 46 passed。
- **保留**:检索 rerank(`memory.native.rerank` cross-encoder)+ B verify-refine(单轨迹迭代 + `validate_patch` 执行硬门控)。
- **未来**:真有 oracle(hwsim/bluez 测试套件就绪 / #50 repro 落地)再按 Agentless filter+vote 重写,**不预建**。
- **详见**:`docs/设计/bug-rca-design.md` §7.6(设计真相)、`.claude/memory/rerank-mechanism-where-it-shines.md`(决策记忆)。

## 坑 #2:Hyperion 侧定位漏斗 —— 建到一半发现与 opencode 重复(2026-07)

### 现象(一句话)
为 bug-RCA 设计 + 起建了一套 Hyperion 自有的 Agentless 式定位漏斗(file→function→line)+ 关键字抽取(regex)+ 方案A 检索预筛(固定管线阶段),结果发现这**与委托目标 opencode 自己的定位能力重复**(double localization),整套砍掉,改成"opencode 自主定位 + Hyperion 把差异化能力做成 MCP 工具给它调"。

### 弯路走了哪几步
1. **初版(把 Agentless 漏斗搬进 Hyperion)**:照搬 Agentless「分层定位 file→function→line」作为**委托前**的固定预筛管线,外加 trigger_parser(regex 抽关键字)+ 方案A(code_index 检索取 top-N 文件喂漏斗)。认为"委托前组装手术刀级上下文"就是 Hyperion 的核心价值,所以这套漏斗得自己建。
2. **起建 + 设计**:建了 trigger_parser 雏形(parse_issue + regex `extract_keywords` + `filter_log_window`);设计并展示了方案A 漏斗代码(检索预筛 → 缩树喂 LLM pick)。
3. **用户质疑 + 三轮调研反转**:用户问"opencode 本来定位能力就很强,加这么多是不是冗余?只调度 + 提供工具是不是更好?"。三轮调研(全流程体检 / agentic RAG / opencode 能力核实)坐实:① 漏斗与 opencode **双重定位**;② 2026 主流是"lead agent + 工具"(deer-flow 2.0 自己都从固定 planner/reporter 图迁到单 SuperAgent + `task` 工具;Claude Code/OpenHands 同款);③ opencode **原生支持** mid-session 调 MCP 工具 → Hyperion 把 recall/search_codebase/filter_logs 做成工具给 opencode 调即可,不必自跑漏斗。→ 整套漏斗砍,改工具驱动委托。

### 根因(为什么是坑)
- **前提没查清(同 #1 rerank)**:建漏斗前没问"**委托目标 opencode 是不是已经会定位?**"——它是强 coding agent,定位本就是其强项。Hyperion 再跑一套 = 重复劳动(double localization,白花一套漏斗的 token/时间)。和 #1"没 oracle 投票平凡"同病:**设计前没核前提**。
- **误搬 Agentless**:Agentless 是**独立 agent**(没有另一个 coding delegate 帮它定位),它的漏斗是"自己定位自己修"。Hyperion 是**委托型**(把活派给 opencode),再在前面套漏斗 = 两个 agent 干同一件事。"Agentless 固定漏斗便宜 ~6×"的教训**仍成立**,但落到"工具内部"(`search_codebase` 工具内部跑廉价检索回手术级锚点),而非"Hyperion 的重复管线"。
- **价值定位偏差**:把"Hyperion 的价值 = 委托前预筛漏斗"想窄了。真正的护城河是 opencode **缺/搞不便宜**的:记忆(跨会话)、code_index 廉价检索、日志过滤 —— 这些做**工具**才有价值,重造定位漏斗没价值。
- **regex 抽关键字逆趋势**:2026 主流是"LLM 自己抽 / agentic 检索"(Claude Code 已弃向量库改 agentic search);regex 抽是偏老派做法,且实测在日志上失败(代码符号 ≠ 日志散文形)。

### 教训(可迁移)
1. **建任何 Hyperion 侧能力前先问:委托目标(opencode)是不是已经会这个?** 会 → 别重复,把 Hyperion **独有的**(opencode 缺的)做成工具给它调。和 [[avoid-overengineering]] 的"查前提条件"一脉相承。
2. **委托型 agent 不建平行管线,建能力工具**:lead agent + 工具 + 调度 + 验证/报告(2026 共识:deer-flow 2.0 / Claude Code / OpenHands)。"工具 > 固定流程"——但**固定/廉价的检索活在工具内部**(search_codebase 内部跑固定 BM25+rerank),控制流是工具驱动。
3. **借鉴要分清"独立 agent"还是"委托型"**:Agentless(独立)的漏斗 ≠ Hyperion(委托型)该建的;搬之前对齐架构形态。
4. **用户对冗余的直觉又对了**(同 #1 rerank)——"是不是加太多了"往往是。该认真调研验证,而非为已建代码辩护。
5. **多轮调研在重度实现前拦住了**:这次只建了 trigger_parser 雏形 + 设计了方案A(没全量接线+测试),损失比 #1 rerank(已全建+测试+三处复用规划)小。**设计阶段调研比实现后反转便宜**。

### 现状(2026-07-31 定稿)
- **砍**:Hyperion 侧定位漏斗(file→function→line)、recall/localize/assemble_localize 三独立节点、方案A 作固定预筛阶段、regex extract_keywords。bug-RCA 流程简化为五步:ingest→delegate_localize_loop(opencode 自定位+MCP 工具)→assemble_repair→delegate_repair_loop→report_memorize。
- **(2026-08-06 补注,R3 收尾 ②[b])**:后来又**加回一个 `recall_lessons` 节点**(流程变六步)—— 但它和被砍的旧 recall **本质不同**:旧 recall 是定位漏斗的一部分(圈锚点喂 opencode = 重复定位);新 `recall_lessons` **只翻记忆、不定位**,把历史同类 bug 教训确定性预进 localize prompt(0 决策 turn 先验),opencode 仍全权自主定位。**不算重造漏斗、不违反本坑教训**(对标 deer-flow DynamicContextMiddleware 的 hybrid 预取)。别看到"又冒出一个 recall 节点"就以为踩坑 #2 复发。
- **改工具**:recall / search_codebase / filter_logs 三能力做 MCP 工具(`hyperion mcp serve`),opencode 经 MCP 按需调,agent prompt 提示优先用(防它裸 grep 烧 token)。
- **代码状态**:文档已全量对齐(docs/设计 6 份已审改);**代码尚未重构**(graph.py 仍 8 节点、localize.py 仍漏斗)——文档领先代码,refactor 记 backlog(见 bug-rca-design.md §9)。
- **详见**:`docs/设计/bug-rca-design.md` §1/§2/§6(设计真相)。

## 坑 #3:delegate 子进程流式读 readline 64KB 行长崩(2026-08)

### 现象(一句话)
R3.1 e2e(`hyperion bug-rca --log <2.6MB 日志>`)早期崩在 `Separator is not found, and chunk exceed the limit` —— opencode `--format json` 事件流里出现 >64KB 的单行(读大文件/大日志的工具结果嵌在一条 JSON 里),delegate 的 `_drain` 用 `async for line in stream` 直接抛 ValueError,整个 run 挂。

### 弯路走了哪几步
1. **初判 R3.1 改动引入**:先怀疑是新加的 MCP 工具 / 砍漏斗有 bug;看栈发现挂在 asyncio 子进程流读取层,跟 R3.1 逻辑无关。
2. **定位 readline 隐式限制**:`async for line in stream` 走 `StreamReader.readline()`,默认 `limit=2**16`(64KB);单行超限**不截断、不等待,直接 ValueError**。
3. **为何 R2 没踩到**:R2 没 `--log`,opencode 只读代码文件(<64KB 居多);R3.1 加了大日志 + filter_logs,opencode 读 2.6MB 日志(或 ~150KB 的 `scan.c`)→ 单条事件 >64KB → 崩。

### 根因(为什么是坑)
- **子进程 stdout 用 readline 读是脆的**:opencode/grep/cat 等 JSON 事件流单条可能很大(文件内容嵌事件里),readline 的 64KB 行长限是**隐式的**——平时不报错,超大行直接崩,没有中间地带。
- R3.0 #56 流式改造选了 `async for line in stream`("逐行流式读"的直观写法),没考虑**单行无上限**的场景。
- 通病同 #1/#2:**没核前提**(readline 的行长限)就用了 API。

### 教训(可迁移)
1. **子进程流式读 stdout 别用 `async for line in stream` / readline**(隐式 64KB 行长限)——改 `read(n)` 块读 + 之后统一 `splitlines()`,行长无上限。
2. delegate 这种"聚全量再 `_parse_stream`"的场景,块读**等价于** readline(反正 EOF 后才解析),没有损失;只有真要"边读边增量处理"才需要按行,而那也该自己缓冲 split。
3. **大输出工具结果要双防**:防流崩(块读)+ 防上下文污染(工具内部封顶 `max_lines` + prompt 禁裸读大文件,见 `filter_logs` 的 400 行上限 + localize prompt 的"禁直接 read 大日志,只调 hyperion_filter_logs")。

### 现状(2026-08-03 定稿)
- `_drain` 改 `while True: chunk = await stream.read(65536)`(块读,行长无上限);e2e 不再早期崩。
- localize prompt 强化"禁直接 read 大日志,只调 `hyperion_filter_logs`"(防模型裸读撑爆上下文)。
- **详见**:`src/hyperion/tools/delegate.py` `_drain`;关联 opencode MCP 接线硬细节(`.claude/memory/opencode-mcp-wiring.md`,含 listTools 5s 超时 / <8KB pipe / PYTHONUNBUFFERED 等同源坑)。

## 坑 #4:被外部进程拉起的服务,相对路径按"调用方 cwd"解析(2026-08)

### 现象(一句话)
R3.1 e2e 产了报告但 `verified:False`、没写 `.patch`;查 `workspace/code` 的 `git diff --cached` 发现有**正确的 .c 改动**(events.c + dbus_new_handlers.c)却混入 `data/memory/memory.db` + `data/code_index/wpa/lancedb/*` 噪声 → `validate_patch` apply --check 挂。

### 弯路走了哪几步
1. 先疑**模型没改码**:git diff --stat(未带 --cached)只见 memory.db,以为 opencode 没动手;后查 events.c 发现已加守卫 —— 是看错了暂存/未暂存。
2. 再疑 **quilt 工作区**(opencode 自己提到 `.pc/` + `series`,以为补丁走 quilt 层 git 看不到)。
3. 最后 `git diff --cached` 才定位噪声源:`hyperion mcp serve`(被 opencode 拉起)把 `data/memory` + `data/code_index` 写进了 `workspace/code/data/`。

### 根因(为什么是坑)
- **opencode 把 MCP server 的 cwd 设成 workspace/code**(`InstanceState.directory`);而 Hyperion config 里 `data/` 路径是**相对的**(`store_path: data/memory`、LanceDB `data/code_index`)→ 按 MCP server 的 cwd 解析成 `workspace/code/data/`。
- 双重后果:① `git add -A` 把这些 data 文件连带暂存 → 补丁脏 → apply --check 挂;② 记忆/索引写到**临时 workspace 库**,不持久(recall 查空、跨 bug 不共享)。
- 通病:**没核前提**("被外部进程拉起时,cwd 还是不是 Hyperion 根")。CLI 自己跑时 cwd=Hyperion 根,相对路径对;被 opencode spawn 时 cwd 变了,相对路径全错位。

### 教训(可迁移)
1. **被外部进程拉起的服务,其相对路径默认按"调用方 cwd"解析** —— 要么 chdir 回自家根,要么 config 路径绝对化(锚到包/配置文件位置)。
2. Hyperion 侧选了前者(`cmd_mcp` 在 `build_server` 前 `os.chdir(Hyperion 根)`):MCP server 是独立进程,工具都用绝对路径/表名(log_path 绝对、codebase 走 env、index 走 repo 名),不依赖 cwd,chdir 无副作用。
3. **诊断补丁问题时,务必看 `git diff --cached`(暂存区)而非 `git diff`**(后者只看未暂存;_observe_patch 用 add -A + diff --cached)。

### 现状(2026-08-03 定稿)
- `cmd_mcp` chdir 到 `_default_config_path().parent.parent`(Hyperion 根);MCP server 的 memory/code_index 路径解析回正轨,补丁干净、记忆持久。
- **详见**:`src/hyperion/cli.py` `cmd_mcp`;`opencode-mcp-wiring` 记忆(同根坑)。

## 坑 #5:workflow 盲信 LLM 结构化输出的 schema(2026-08)

### 现象(一句话)
R3.1 e2e #2 崩在 `1 validation error for Evidence / line / Input should be a valid integer ... input_value='3067,4105,5980,8452,9818,10326,10682'` —— glm-5.2 的 `evidence[].line` 给了**逗号多行串**而非单个 int,`node_report_memorize` 直接 `Evidence(line=<串>)` → pydantic 崩 → 整个 bug-rca 崩。

### 弯路走了哪几步
1. e2e #1 同一处没崩(那轮 line 是 None/空,`Evidence(line=None)` 合法)→ e2e #2 line 变成逗号串才崩 —— **LLM 输出方差**,不是稳定复现的代码 bug。
2. 意识到 schema(JSON Schema 声明 `line: integer`)是**契约不是保证**:LLM 偶尔不守(尤其 glm-5.2 给多嫌疑行逗号串),喂进 pydantic 严格模型就崩。

### 根因(为什么是坑)
- **LLM 输出 → pydantic 严格模型** 的边界没做防御:node_report_memorize 盲信 `e.get("line")` 是 int,直接构造 `Evidence`。
- schema 声明不等于 LLM 遵守:DeepSeek/glm 等在结构化产出上有方差(类型不符、多值合并、字段缺失)。pydantic 严格校验 → 单条坏数据崩整个流程。
- 通病:**没核前提**("LLM 会守 schema")—— 同 #1/#2/#3/#4 一脉。

### 教训(可迁移)
1. **LLM 输出喂进 pydantic 严格模型,必加防御 coerce**(int/float/"3067"/"3067,4105"/"3067-3070"/None 全处理,取首个有效值)+ **单条坏不连坐**(try/except 跳过这条,继续)。
2. **schema 是契约不是保证**:delegate(`--format json`)吐的结构化输出,边界处都要当"不可信输入"处理(coerce + 容错 + 降级),不能裸塞严格模型。
3. 这类 bug **e2e 才暴露**(方差性,单测难复现)—— 长尾,逐个 coerce;真要根治得换"LLM 重试到守 schema"或"宽松解析",但成本高,先 coerce 兜底。

### 现状(2026-08-03 定稿)
- `_coerce_evidence_line`(int/float/逗号串/区间串/None 全处理)+ evidence 循环 try/except 跳坏行;单测全 case 过。

## 坑 #6:chunker #58 —— 只修符号路径,漏了 module 路径(2026-08)

### 现象(一句话)
`hyperion index wpa` 撞 400 "Range of input length should be [1, 33000]";照 backlog #58 给 chunker 加了"超长符号按行区间再切"(`_symbol_to_chunks`),离线扫 backlog 点名的 driver_nl80211.c —— max 12275,**根本没超**;真肇事文件 qca-vendor.h 仍是单 chunk **304044 字符、没被切**。

### 弯路走了哪几步
1. 看 backlog #58 写"driver_nl80211.c / qca-vendor.h 有超长符号"→ 以为根因是"符号整块切、符号路径缺 max-chunk-size 兜底"。
2. 加 `_symbol_to_chunks`(符号路径切分)+ 单测 + 离线扫这两个文件验:driver_nl80211.c max 12275 ✓,以为成了。
3. **离线全仓扫一眼才发现**:qca-vendor.h chunks=1 / max=304044 / over_cap=1 —— 它**没有任何被解析的符号**(C 的 `class_node` 故意 `_none_` 不匹 struct 降噪,header 又无 function_definition)→ 整个文件落进 `_module_chunk`(模块级兜底),而 module 路径**没有 max-chunk-size 上限**。又补 `_module_chunks`(模块路径切分)才真修好。

### 根因(为什么是坑)
- **backlog 的根因描述只点了"符号路径"**,没区分符号路径 vs 模块路径两条产 chunk 的路径;照单实施就漏了一半。
- **"无符号文件"是 C 头文件的常态**(struct/union/typedef/宏,不进 function_definition 且 struct 被配置故意跳过)→ 这类文件 100% 落 module chunk;module 路径无上限 = 埋雷。
- **离线只验"backlog 点名的文件"不够** —— driver_nl80211.c 是红鲱鱼(它的代码都在被解析的函数里,各 <12K);真肇事的是 qca-vendor.h。该验的是**全仓 max chunk size 聚合**,不是"backlog 点名的样本"。

### 教训(可迁移)
1. **修"无上限"类 bug,要把所有产生该产物的路径都过一遍**,不只 backlog 点名的那条(chunker 有符号 + 模块**两条**产 chunk 路径,都得加上限)。
2. **离线验证用"全仓聚合统计"(max / over_cap 计数),别只验"backlog 点名的样本"** —— 红鲱鱼样本会让你误判已修。免费且能吃定心丸,花不了几秒。
3. **C 头文件常无被解析符号**(struct 被故意跳过降噪)→ 它们全进 module chunk;module 路径的健壮性和符号路径同等重要,别当"兜底"轻视。

### 现状(2026-08-03 定稿)
- `_symbol_to_chunks`(符号路径)+ `_module_chunks`(模块路径)都按行区间二次切分到 ≤ `MAX_CHUNK_CHARS`(16000);复用预留 `part/total` + 独立 `content_hash` + 真实行号。`_SKIP_DIRS` 加 `.pc`。
- 权威回归:`hyperion index wpa --force` → **12490 chunk 全绿、无 400**(不只 chunker 层离线证,真 embedder 端到端验过)。
- **详见**:`src/hyperion/services/code_index/chunker.py` + `.claude/memory/backlog-production-grade.md` #58(留档段含 module 路径发现的来龙去脉)。

## 坑 #7:research 子 agent 撞 recursion_limit 全丢 —— reasoning 模型不收敛,得优雅降级(2026-08)

### 现象(一句话)
R3.2 deep_research e2e 的 8 个模块子 agent **几乎全部** `(调研失败)` —— 每个都一路探索到 `GraphRecursionError: Recursion limit reached` 还没收尾吐 JSON,异常一抛,**前面几十轮工具调用收集的证据全丢**,finding 变成空白。调大 limit(25→50→60)、改 prompt 叫它"早收尾"都治不好(8/8 照撞)。

### 弯路走了哪几步
1. **初判:预算太低**。第一轮全 `GraphRecursionError`,以为 `recursion_limit=25` 给少了 → 引入 `_RECURSION_LIMIT=_MAX_TURNS*2`(因为发现 LangGraph 的 recursion_limit 按 *superstep* 计、ReAct 每轮=2 superstep,`_MAX_TURNS=25` 当 recursion_limit 实际只给 ~12 轮)。这是真 bug,但修了只多救 1-2 个模块。
2. **再判:prompt 没教它收尾**。加"节奏控制"提示(search_code 起步、只读关键函数、~10 次就出 JSON、别耗光)。模型**根本不听** —— 8/8 照撞。
3. **直接测工具才发现真相**:把三个 @tool 单独跑(`grep_symbol`/`read_function`/`search_code`)—— **返回极其精准**(wpa_supplicant_init@6362、nl80211_send_frame_cmd 片段…)。工具没问题、证据很充足,**问题在模型行为**:deepseek-v4-pro(reasoning/thinking)拿到好工具就忍不住一直读"再看一个",**永远不会在预算内自己收尾**。
4. **根因顿悟**:`GraphRecursionError` 是**硬墙**——它在 superstep 超限时 `raise`,而 `ainvoke` 一抛异常就**什么都不返回** → 几十轮 grep/read 收集的证据**全部丢弃**(不是"还没总结",是"连总结的机会都没有")。所以加预算/改 prompt 都是隔靴搔痒:**真正要修的是"撞墙时别把工作全丢"**。

### 根因(为什么是坑)
- **递归上限是硬抛异常、不是软停止**:LangGraph `recursion_limit` 超限 → `GraphRecursionError` → `ainvoke` 无返回值。ReAct agent 的"工作"(tool_calls + 工具结果)只在 agent 的内部 state 里,异常一抛调用方拿不到 → 全丢。和 readline 64KB 直接 ValueError(坑 #3)同病:**隐式硬限制,超了就崩、没有中间地带**。
- **reasoning 模型 + 好工具 = 过度探索**:thinking 模型倾向"再确认一个",prompt 约束力很弱。调大 limit 只让它多撞几轮墙再丢,不解决问题。
- **盲信"agent 会自己收尾"**:设计时假设子 agent 跑够了就吐 JSON,没考虑"它就是不吐"的退化路径 → 没做兜底。
- 通病(同 #1/#2/#5):**没核前提**("agent 会在预算内收敛")。

### 教训(可迁移)
1. **ReAct 子 agent 别指望它自己收尾 —— 撞 recursion_limit 要优雅降级,不能硬抛全丢**。模式:`astream(stream_mode="values")` 流式留最后一份 state(含全部 messages),`except GraphRecursionError:` 把已收集证据(`_compact_evidence` 压成文本)喂回**裸模型**(不带 tools,逼它只产文本)做一次强制总结。这样"不收敛"也至少拿到一份基于真实 file:line 的 finding,而非空白。
2. **`recursion_limit` 按 superstep 计,不是"轮"**:标准 ReAct 图(model 节点 + tools 节点)每轮 = 2 superstep。想给 N 轮预算就 `recursion_limit = 2*N`。变量名叫 `_MAX_TURNS` 时尤其要当心单位。
3. **诊断"agent 失败"先直接单测工具**(便宜、快)——工具返回正常就把锅从工具挪开,聚焦 agent 行为/预算/收敛。
4. **prompt 约束不住 reasoning 模型的探索冲动** —— 别把"prompt 让它早停"当可靠的防跑飞手段;结构性的降级(catch + 强制收尾)比 prompt 可靠。

### 现状(2026-08-03 定稿)
- `_research_one_module` 改 `astream` + `except GraphRecursionError` + `_compact_evidence` + 裸模型 `_FORCED_SUMMARY_PROMPT` 强制产 JSON;`_MAX_TURNS=20`(`_RECURSION_LIMIT=40`)。
- smoke 验证:即使 `recursion_limit=8`(≈4 轮)降级路径也能产 **8 条真实 cited finding**。
- e2e 实测:8 模块全走降级、**0 失败**,报告 80 条引用全核验通过(0 幻觉),`CodebaseFact 入记忆: 8 条`。
- **详见**:`src/hyperion/workflows/deep_research/_research.py` `_research_one_module` / `_compact_evidence` / `_FORCED_SUMMARY_PROMPT`;关联 [[runtime-middleware-policy]](LoopDetection/TokenBudget 是防跑飞,recursion_limit+降级是防"撞墙全丢")。

## 坑 #8:@tool 在线程池里懒导入重模块 —— `_DeadlockError`(2026-08)

### 现象(一句话)
为验证坑 #7 的降级,直接单测 `_research_one_module` —— 立刻崩在 `_DeadlockError: deadlock detected by _ModuleLock('hyperion.services.code_index.embed')`,而不是预期的 `GraphRecursionError`。三个 @tool(`grep_symbol`/`read_function`/`search_code`)的函数体里都写了 `from hyperion.services.code_index.xxx import ...` 懒导入。

### 弯路走了哪几步
1. 单测一跑就 `_DeadlockError`,栈顶在 tool 执行 → 一度以为**这才是 e2e 8/8 全挂的真凶**(比 recursion 更基本)。
2. 但 e2e 日志里全是 `GraphRecursionError`、**没有** `_DeadlockError` —— 矛盾。回看 graph 节点顺序发现:`node_index`(在 `node_research` **之前**)已经 `import` 并用过 `code_index.embed/parser/store`,模块早进了 `sys.modules` 缓存;e2e 里工具再 import 只是查表,**不触发**死锁。
3. 而单测直接调 `_research_one_module`、跳过 `node_index` → 工具是**首次**导入这些模块 → 在 langgraph 的 tool 线程里 import → 死锁。即:**e2e 被前序节点的副作用"恰好掩盖"了一个真存在的潜伏坑**。

### 根因(为什么是坑)
- **langgraph 的 tool_node 用线程池跑工具**(`run_in_executor`),工具函数第一次执行时在**工作线程**里 import 重模块,而该模块的包 `__init__` 又导入一串子模块 → Python 的 import lock(`_ModuleLock`,**非重入**)在线程间争用 → `_DeadlockError`。
- **懒导入放在 @tool 函数体里**是为了"不 import research 就不载重模块",但埋了线程死锁的雷。
- **被前序节点的副作用掩盖**:e2e 碰巧先跑了 `node_index`(预载了这些模块),工具线程只剩 `sys.modules` 查表,不撞锁;换任何**跳过 index** 的调用方(单测、别的 workflow、临时脚本)必挂。这种"e2e 绿、单测红"的坑特别隐蔽。

### 教训(可迁移)
1. **@tool / 任何被线程池调的函数,别在函数体里懒导入重模块** —— 提到**模块顶层**(主线程一次性载入,工作线程只剩查表)。langgraph 的 tool、asyncio `to_thread`、`run_in_executor` 都算。
2. **"e2e 过、单测挂"先怀疑导入/cwd/时序差异**:某个前序步骤(import、chdir、env)在 e2e 里顺带把前提满足了,单测没那步就露馅。对照调用路径差异定位。
3. 懒导入想省"不调用就不载入"的成本,代价是**把导入时机推到不可控的线程里** —— 对重/共享模块不值;真要省,用显式的延迟初始化函数(在主线程调一次),别靠 import 副作用。

### 现状(2026-08-03 定稿)
- `code_index` 的 4 个 import(`embed.create_embedder` / `parser.iter_source_files,parse_file` / `retrieval.create_reranker,retrieve` / `store.LanceDBStore`)提到 `_research.py` 模块顶层;三个 @tool 删掉函数体内的懒导入。直接单测不再死锁。
- **详见**:`src/hyperion/workflows/deep_research/_research.py` 顶部 import 段(含注释说明为何必须顶层);同根的线程/子进程隐式坑见坑 #3(readline 64KB)、#4(cwd)。

## 坑 #9:TurnBudget 中间件"接上了但不生效" —— 中间件 hook 是独立图节点,recursion_limit 按 superstep 计把每轮算成 2 是错的(2026-08)

### 现象(一句话)
R3.2.x P1 给 research 子 agent 加 `TurnBudgetMiddleware`(max_turns=20,warn@19/strip@20)想治"撞 recursion_limit"。代码完 + 单测 80 绿,但**真模型 e2e 一跑,3 个模块照样撞 `recursion_limit(44)`** —— TurnBudget 的 strip 根本没机会触发。日志只看到 `Turn budget hard stop` 一次(还是某模块恰好到 20),多数模块在 turn ~6 就被递归墙截了。

### 弯路走了哪几步
1. **初判:中间件 keying 错**。TurnBudget 按 `run_id` 分桶,取不到就 fallback `id(runtime)`。核 langchain 1.3.14 源码确认 `aafter_model` hook 名对、确实被 `create_agent` 注册成节点、确实每轮被调 —— hook 本身没毛病。但 `runtime.context` 里**根本没有 `run_id`**(config 只设了 `thread_id`),于是永远走 `id(runtime)` 兜底;而 `Runtime` 对象每个 superstep 可能新建 → `id` 每轮变 → **计数每轮清零 → 永远到不了 max_turns**。改成按 `thread_id` 分桶(同 LoopDetection),单测加"每轮换新 runtime 对象、只 thread_id 不变"的回归测 —— 这修了 keying,但 e2e 还是撞墙。
2. **写集成探针隔离变量**:用桩模型(永远吐 tool_call)+ 真 `create_agent`,recursion_limit 给超大(200)→ **run 干净结束、strip@max_turns 生效、不崩**。把 recursion_limit 调回 (max_turns+2)*2 又崩。结论:**strip 机制本身没问题,是 recursion_limit 太低抢在 strip 之前撞墙**。
3. **核 `create_agent` 源码才顿悟**:每个中间件的 `after_model`/`before_model`/`before_agent`/`after_agent` 都是**独立的图节点**(`graph.add_node(f"{m.name}.after_model", ...)`),各算 1 superstep。所以一轮 ReAct 实际消耗 `1(model) + N(after_model 链) + 1(tools) = N+2` superstep,**不是 2**。5 个中间件 → 每轮 ~7 superstep,`recursion_limit=44` 只够 ~6 轮,TurnBudget 的 `max_turns=20` **永远到不了**。

### 根因(为什么是坑)
- **坑 #7 教训 #2 的"每轮=2 superstep"是不完整的真相**:那只对"裸 ReAct 图(只有 model + tools 两节点)"成立。**一旦挂中间件,每个 hook 变独立节点,每轮 superstep 数 = 2 + (有 after_model 的中间件数)**。`_RECURSION_LIMIT=(max_turns+2)*2` 按每轮 2 算,严重低估 → 递归墙在 TurnBudget 之前先撞。这是坑 #7 的进阶版(同是"recursion_limit 单位",只是这次漏算的是中间件节点)。
- **中间件的 keying 不能用对象身份**:`id(runtime)` / `id(any_obj)` 在"框架每个 superstep 可能注入新对象"的场景下不稳定。要用框架保证整 run 不变的标识(LangGraph 里是 `configurable.thread_id`,但它进 `runtime.context` 需要框架传播 —— 本版 `runtime.context` **不自动**含 thread_id,得显式传 context 或接受 "default" 兜底)。
- **单测给了虚假信心**:单测用一个稳定 SimpleNamespace 对象反复调 after_model,`id` 不变 → 计数累积 → 绿。但真 runtime 每轮新对象 → 红。**"单测绿、集成红"的典型:单测的手工桩没复刻框架的对象生命周期**。
- 通病(同 #7/#8):**没核前提**。这次前提是"中间件 hook 不增加 superstep / runtime 对象身份稳定",两个都错。

### 教训(可迁移)
1. **`recursion_limit` 按 superstep(图节点执行)计;中间件的每个 hook(before/after_model/agent)都是独立节点**。挂了 N 个有 after_model 的中间件,一轮 ReAct ≈ N+2 superstep,不是 2。设 `recursion_limit` 要按**真实中间件数**算:`max_turns × (N+2) + 启动/收尾 margin`,或给一个远大于 `max_turns×(N+2)` 的固定兜底值。别用 `2×max_turns`(那只在裸图成立)。
2. **中间件按 run 分桶别用 `id(obj)`** —— 用框架保证 run 内稳定的标识(thread_id / 显式传的 context)。写单测时**故意每轮换新对象**(只保留稳定标识)才能复刻真生命周期,否则单测绿得虚假。
3. **"中间件接上了但不生效"先写集成探针隔离**:桩模型 + 真 `create_agent` + 超大 recursion_limit,几秒内确定性复现"hook 是否被调 / strip 是否终止 loop / keying 是否累积",比烧 15min 真模型 e2e 便宜得多。探针留 `/tmp`(不提交)。
4. **诊断"X 没生效"分两层**:① X 的 hook 被调了吗?(看日志/加探针)② 被调了但被别的东西抢了先吗?(recursion_limit / 别的中间件 / 路由)。本案两层都中:keying 让 hook 计数清零(①),recursion_limit 又抢在 strip 前撞墙(②)。

### 现状(2026-08-03 定稿)
- `turn_budget.py`:分桶键从 `run_id`/`id(runtime)` 改 `thread_id`(同 LoopDetection);`consume_stop_reason` 同步改参。单测加 `test_counting_keys_on_thread_id_not_object_identity`(每轮换新 runtime 对象,只 thread_id 不变)锁回归。

## 坑 #11:glm-5.2 系统性把根因误诊成「显眼日志行」—— bug-RCA 验证门控的盲区(2026-08)

### 现象(一句话)
bug-RCA demo2(wpa_supplicant P2P scan 孤儿 radio work 泄漏)**连续 3 次 e2e**(e2e#2 pivot 轮 / R3 老 orchestrator / e2e#4)glm-5.2 都把根因误诊成「`wpas_find_stopped` 的 **abort 失败**分支不释放 `p2p_scan_work`」,而**金标准根因**是更早 7 秒的「并发 D-Bus `Interface.Scan` 覆写 `scan_res_handler` → 扫描完成事件**误路由**到 `scan_only_handler` → 不释放」。三次都 `applies=True`、四道硬门全过、`verified=True`,**但根因错、补丁治标且碰巧能 work**。

### 弯路走了哪几步
1. **e2e#2(pivot 轮)**:agent 定位到 abort 失败路径,产补丁(abort 失败时释放孤儿)。validate×2 过、memorize 入库,当时记为「补丁落点不错」。
2. **R3 老 orchestrator**:同样 abort-fail 落点(记忆 r3-memory-closure-handoff 已标「delegate 产次优补丁」)。
3. **e2e#4(本轮)**:agent **再次**误诊 abort-fail;报告「证伪」段只在错误假设内自洽(只查「abort 失败后有无别的释放路径」,没查「孤儿是不是在 abort 失败*之前*就形成了」)。拿金标准一对比才穿帮:**孤儿 10:12:12(误路由)就形成,abort 失败 10:12:19(StopFind)才发生 —— 因果时序倒置**。

### 根因(为什么是坑)
- **注意力被显眼日志行劫持**:`Abort scan failed: ret=-2 (-ENOENT)` 是 ERROR 级、显眼,glm-5.2 抓它当根因下手点;真成因 `Scan-only results received`(line 2452,误路由)是 INFO 级、安静,被忽略。
- **确认偏差持续:围着假设收集支持证据,避开反证**(anchoring 的延续,比"抓显眼行"起点更难纠,贯穿整个取证):agent 一旦锚定 abort-fail,**后续所有取证都围着它转** —— `filter_logs` 从 abort 时刻(10:12:19)切窗(漏掉 7 秒前的误路由起点 line 2452)、`grep` 用 `abort`/`ENOENT`/`ret=-2` 这些**假设词**(只命中支持假设的行)。filter_logs/grep 本是中立工具,被假设驱动后成了**确认偏差放大器**:agent 从不主动 grep 反证词(如 `scan_only`/`misroute`/`scan_res_handler`)去找推翻自己的证据。
- **filter_logs 切了时间窗但没标因果起点**:窗口(10:12:10–10:14:00)里的精华行没把「最早那条关键事件」标成主角,agent 注意力被窗口内更响的 abort 失败吸走。
- **证伪没跨假设边界**:SKILL 的「证伪」是「找推翻当前根因的反例」,但 agent 在错误假设内证伪,没问「这个现象是不是在 purported 根因*之前*就存在了」(时序一致性检查缺失)。
- **验证门控只查 apply,不查根因正确性**(最大盲区):`validate_patch` 是执行硬门(`git apply --check`),不判「根因对不对 / 补丁治不治本」。**四道硬门全过 ≠ 根因对。**
- `-ENOENT` 是**症状不是原因**:扫描结果 10:12:12 早已到达(被误路由没清状态),StopFind(10:12:19)去 abort 一个「早已完成、状态没清」的扫描 → 驱动当然回 -ENOENT。agent 把「扫描已完成但状态没清的症状」当成了「孤儿的原因」。

### 教训(可迁移)
1. **LLM 的 RCA 会系统性抓「显眼日志行」当根因,忽略更早、更安静的因果链起点**。对抗:① filter_logs / 报告模板**显式标注因果起点**(最早那条关键事件,而非最响的);② 证伪必须跨假设边界 —— 问「这个现象是不是在 purported 根因*之前*就存在了?」做**时序一致性检查**。
2. **apply 通过 ≠ 根因对**。当前验证封顶(apply/build)对「补丁能不能打」有效,对「根因对不对 / 补丁治不治本」**无效**。要堵这个盲区:R5 Tier1 运行时验证(打补丁回放日志,看孤儿是否在 purported 成因点真消失)+ 或加一道「第二轨迹独立 RCA 再交叉比对」(对抗审 / 多轨迹一致性,落到根因而非补丁)。
3. **同一 bug 多次 e2e 反复同一误诊 = 模型偏差,不是偶然**。出现系统性误诊别当「这次运气差」,要当「流程有盲区」—— 在 SKILL / 工具层加针对性引导(本案:因果起点标注 + 时序证伪)。
4. **有金标准时,e2e 后必做对比**(落点 / 机制 / 时序是否自洽),别只看 apply 过就收工。demo2 是罕见的带 oracle 场景,该用它**校准 RCA 能力**,而不只是验流程跑通。
5. **LLM agent 锚定初步假设后,会围着它收集支持证据(切窗从假设时刻、grep 假设词),系统性避开反证** —— anchoring 的延续,贯穿整个取证,比"抓显眼行起点"更难纠。对抗:① 主动 grep **反证词**(不只假设词);② filter_logs 从**比现象/假设更早**切(别从假设时刻);③ 强制"找推翻假设的证据"而非找支持。**确定性手段(filter_logs 边界提醒 / 因果起点注入,方案 A)比 soft 提醒(prompt 说"要找反证")可靠** —— e2e#5 证 soft 不管用。

### 现状(2026-08-07 记,含 e2e#5 实证)
- **未改代码**(模型行为 + 流程盲区,非代码 bug)。e2e#2/#4/#5 产物均为误诊样本(abort-fail 落点),留作与金标(`example/demo2/fix-p2p-scan-orphan-minimal.patch` + 人写报告)的对比存档。
- **短期(soft 层)已验证无效(e2e#5,2026-08-07)**:给 SKILL 加了「因果起点标注 + 时序证伪」+ agent prompt 加「时序检查」(commit `1e47d38`),e2e#5 同 demo2 跑 —— **仍第 4 次误诊 abort-fail**(落点 `wpas_find_stopped`)。且机制比"忽略指令"更深:
  - **agent 照做了时序证伪,但问错问题**:报告有"时序一致性检查"段,却只验"abort 失败(10:12:19)早于联网失败(10:13:46)"(trivially 成立),没验"孤儿(p2p_scan_work 泄漏)是否早于 abort 失败形成"(真问题)。**soft 指令没规定"查哪个时序",agent 选了最易通过的 → 在错误假设内被自洽满足。**
  - **记忆先验反噬(意外发现)**:recall 出踩坑#11 警告("glm-5.2 会误诊成 abort-fail,实为误路由"),但 agent 用一个**错误事实判断把它"证伪"了** —— 称"日志无 `NEW_SCAN_RESULTS` → 结果不会回来 → 不是误路由",而实际日志 line 2452 `Scan-only results received` **正是**结果到达的证据(只是去了 scan_only_handler)。**警告类记忆被模型当"待证伪假设"给证伪了,反而强化错误自信。** 记忆先验不是万能药。
  - **filter_logs 切片漏了因果起点行**(line 2452),agent 全程被 `Abort scan failed: ret=-2` 锁死注意力,没看到误路由铁证。
- **✅ e2e#6 转折(2026-08-07,加方案 A 边界提醒 + 新 SKILL"从更早切"后):命中金标准!** filter_logs 这次切对窗(since=10:12:00,e2e#5 是 10:12:19)→ 覆盖误路由起点 10:12:12 → agent 看到 `Scan-only results received`(line 2452)→ 抓到误路由根因 → 补丁落点 = 金标(`scan_only_handler` + `wpas_p2p_scan_work_done` + `p2p_scan_res_handled`,3 文件逐行一致)。**证:切窗起点是关键杠杆 —— 切对窗 → 看到起点 → 金标;方案 A(边界提醒)+ 新 SKILL("从更早切")方向对。** ⚠️ 但**单次成功**,glm-5.2 有方差(本坑系统性偏差),不能宣称"治了";要多跑几次 e2e 确认命中率(e2e#5 误诊 / e2e#6 命中,目前 1:1,不足以下结论)。即便如此,e2e#6 证明"切窗杠杆"真实存在,工具层(强制注入起点)是正解方向。
- **结论:soft 层(prompt/SKILL/记忆警告)对这种系统性 RCA 偏差不奏效**(踩坑 #7「prompt 约束不住模型注意力」的 RCA 版)。真正解是**确定性**的:
  - **中期(工具层)—— 2026-08-10 A/B 验证后定稿(LLM 自己控窗口 + 漏根因提醒,弃 prepend/lookback)**:
    - **prepend 证伪**(A/B 裸 LLM 对照,deepseek × 各2轮,demo2):partial + 反方 —— B 打破时间 anchoring(2/2 根因从 abort `:19`→`:12`),但 coalesce 漏金标行(`Scan-only results received` 被该秒 1130 行 wpa 噪声淹没、窗内排第 1626),只给 `:12` 次优事件(`CANCEL_REMAIN_ON_CHANNEL`),**反把落点从金标 `scan_res_handler` 带偏到 ROC**。去噪命中需重度日志清洗(接近 log template mining,YAGNI/过拟合)。**prepend 过度设计,放弃**。

## 坑 #12:bug-RCA 流程假设错 —— "单 session 一次走完 + apply 验证够"(2026-08)

### 现象(一句话)
原 SKILL 设计成固定 9 步流水线 + 单 session 4 硬门(validate/export_patch/memorize/export_report),隐含"补丁/报告一次到位 + apply 过即修对"。e2e#4/#5 实测穿帮:补丁 plausible 非金标(连续误诊 abort-fail,见 #11),`validate_patch` 过 ≠ 修对(系统软件无单测,真机才是 oracle)—— "一次走完 + 自动验证够"的假设站不住。

### 弯路走了哪几步
1. 9 步流水线强制"一个 session 走完",步数将尽优先硬门。
2. 把 `validate_patch`(apply 校验)当"补丁修对了"的判据。
3. memorize/export_report 在单 session 未经验证就做(把没坐实的根因/补丁写进记忆)。

### 根因(为什么是坑)
- **假设"自动验证(apply)够"**:apply 过只证明补丁能打,不证明修对;系统软件无单元测试,真机/复现是唯一 oracle(METR:test-passing PR 约一半不 merge)。
- **假设"一次走完"**:bug 根因很少一次猜中、补丁很少一次到位(POPPER/RepairAgent 都证明 RCA/补丁是迭代循环)。
- 通病(同 #11):**没核前提**("自动验证够吗?能一次到位吗?")。

### 教训(可迁移)
1. **bug-RCA 是迭代,不是一次走完**:假设↔证伪循环 + 补丁↔验证循环(对标 POPPER ICML2025 / RepairAgent ICSE2025)。
2. **`validate_patch` 只验 apply,不是"修对"判据**;真机/人是 oracle。每版补丁 export_patch 交人验证。
3. **memorize/report 是验证后的收尾**,不是单 session 硬门;未验证就 memorize = 污染记忆(接 #11 记忆反噬)。

### 现状(2026-08-07 定稿)
- SKILL/agent 改**工具箱 + 人在环迭代**(commit `deeab6c`/`b6ba4bd`):去固定顺序;memorize/export_report 降为验证后收尾;validate 定位"只验 apply";真机 oracle。
- e2e 方法学改:单 session 跑到 export_patch(交人验证),非走完。
- 关联:[[pitfall-log]] #11(RCA 误诊,本坑姊妹——#11 是模型偏差,#12 是流程假设错)、[[bug-rca-skill-toolbox-hitl]](范式转向产物)。

## 坑 #13:skill/prompt 受众错位 —— 写给人(面向小白/项目叙事)而非模型(2026-08)

### 现象(一句话)
SKILL.md / agent prompt 里塞了"面向小白"教学口吻(类比"手术刀+记忆")+ 项目内部叙事(踩坑 #11 编号、glm-5.2 连续误诊史、e2e#5 复盘、对标 POPPER/RepairAgent/METR、commit 日期/重写记录)。skill/prompt 受众是**模型**(读它来决定怎么用工具),这些是噪声——烧 context,不指导行为。

### 弯路走了哪几步
1. 把 SKILL.md 当"文档"写(给人读),教学口吻 + 类比铺垫。
2. 项目教训直接塞进 SKILL("踩坑 #11 教训是…"),用内部叙事包装。
3. 没区分"给模型的指令" vs "给人的文档/踩坑"。

### 根因(为什么是坑)
- **受众错位**:skill/prompt 给模型(指令消费),文档/踩坑给人(阅读理解)。模型 context 窗口宝贵,叙事/教学/历史性内容是噪声。
- **项目内部知识泄漏到指令**:踩坑编号、模型误诊史、对标论文 —— 模型不需要知道这些来决定行为;它需要可执行指令。
- 通病:**没想清受众**(模型 vs 人)。

### 教训(可迁移)
1. **skill/prompt 面向模型**:指令性(祈使/"你负责…"/Use when),不教学(无"面向小白"、无类比铺垫)。
2. **项目内部知识不进 skill/prompt**:踩坑编号、模型误诊史、e2e 复盘、对标论文、commit 日期 —— 留 `docs/踩坑记录.md` + `.claude/memory/`(给人/跨会话)。
3. **description = 触发器**(what + when + 关键词),不是营销/介绍;模型靠它决定是否触发。
4. **教训提炼成可执行指令**(如"从更早切日志""做时序检查"),别叙事包装("踩坑 #11 教训…")。

## 坑 #17:opencode 配置两处真理源无同步 —— 加 agent 没生效,改成 symlink 单源(2026-08)

### 现象(一句话)
backport skill 落地后,`opencode agent list` 看不到 `hyperion-backport` agent;更糟的是 cwd 根 `opencode.json` 还引用 2026-08-10 已撤的 `hyperion_filter_logs`(幽灵工具)。根因:opencode 从 cwd 根读 `opencode.json`,但 Hyperion 把"模板"放 `config/opencode_hyperion.json`,**两个文件都在 git 里且无任何同步机制** —— 加 agent 时只改了模板,实际加载的 cwd 根文件没动。

### 弯路走了哪几步
1. 加 `hyperion-backport` agent block,只 commit 模板 `config/opencode_hyperion.json`(commit `9311973`),以为模板生效。
2. e2e 跑前发现 opencode 看不到 backport agent —— 实际加载的 cwd 根 `opencode.json` 停在旧版(缺 backport + 还引用已撤的 filter_logs)。
3. 应急 `cp config/opencode_hyperion.json opencode.json`(模板是正确源头)commit `3a12721` 修过;但这是手工同步,**下次改模板还会忘 cp**。
4. **根治**:cwd 根 `opencode.json` 从普通文件(100644)改 symlink → `config/opencode_hyperion.json`(git mode 120000),从此只有一份真理源,改模板透 symlink 立刻生效。验证:改模板加临时 agent → `opencode agent list` 立刻看到 → 移除。

### 根因(为什么是坑)
- **opencode 从 cwd 根 `opencode.json` 读配置,不从 `config/` 读** —— 这个加载路径在设计时没核清(同 #1-#5 通病:没核前提)。于是"模板"和"实际加载"成了两个独立真理源。
- **两处真理源 + 无同步机制 = 漂移必然**:改一处不碰另一处,时间长了两份必然不一致。这是"配置漂移"类 bug 的温床,比"忘改"更深 —— 是**架构上就允许漂移**。
- **幽灵工具引用**:不只"缺新 agent",旧文件还残留已撤工具(filter_logs)的引用 —— 说明这个文件**长期没人维护**,彻底背离了模板。

### 教训(可迁移)
1. **配置只有一个真理源**:多处真理源 + 手工同步 = 必漂移(每次改都要记得 cp 两处 = 人来保证不变量,迟早失败)。要么 symlink(单文件真理源,透链生效),要么代码生成(模板 + 渲染),要么 CI 校验两份一致。**别靠"开发者每次记得改两处"。**
2. **设计配置加载前先核"实际从哪读"**(同 #4 cwd 漂移、#10 opencode 加载路径的通病):opencode 从 cwd 根读不是从项目结构猜的路径读;没核清就放"模板"到别处 → 立刻两源。
3. **symlink 跨机注意**:Linux/macOS git 正常还原 symlink;**Windows 默认不解**(写成含路径文本的普通文件)—— 上 Windows 需 `git config core.symlinks true` + 开发者模式。Hyperion 两台机 Linux/macOS 不受影响。
4. **诊断"配置没生效"先确认加载路径**:`opencode agent list`(或等价的"列出实际生效配置")比"看模板对不对"靠谱 —— 模板对了不代表被加载。

### 现状(2026-08-12 定稿)
- cwd 根 `opencode.json` = symlink → `config/opencode_hyperion.json`(commit `75ab78a`)。两关验证全绿:① `opencode agent list` 透 symlink 列出全部 5 agent;② 改模板加临时 agent 立刻可见。
- **详见**:`src` 无改动(纯配置);关联 [[opencode-config-drift]]、[[opencode-mcp-wiring]](踩坑 #10 opencode 加载路径同源)。

## 坑 #18:recall 命中但 agent 不短路 —— 召回层工作了,注入层写成流水线把它浪费了(2026-08)

### 现象(一句话)
compare skill 的「首次调研→读码即记→下次 recall 命中→零重跑秒答」价值闭环,e2e 热路径(记忆已有同主题对比事实)实测**没短路**:recall 第一步就命中(两 codebase 各召回 1245/894 字符完整对比事实),但 agent 仍整轮重跑 —— read×22 + search×4(42 工具 vs 冷路径 44),还重复 memorize×2。agent 自述:「记忆已命中,但按 compare skill 流程我需要重新跑一遍读码验证」。改 SKILL 加「recall 命中就短路」指令后:42 工具 → 4 工具、read 22→0、~4min→~40s(7× 提速),报告质量不降。

### 弯路走了哪几步
1. 设计 recall-first 调研 skill(compare/onboarding),以为"第一步调 recall"=「命中就短路」。
2. e2e 热路径实测穿帮:recall 命中了,agent 却当"参考",仍走完整 7 步 playbook 重跑。
3. 初判"召回层没工作" → 核 recall 返回,命中完整事实,**召回层没问题**。
4. 定位到**注入层 gap**:SKILL.md 把流程写成固定 7 步 playbook,agent 当「每次必走完」的流水线,recall 命中后没敢短路(它忠实执行了"走完流程")。
5. 修法:SKILL + agent prompt 改「recall 优先 + 命中短路」—— 命中同 codebase 同主题完整事实 → 直接复用出报告,不 search/read/memorize;短路路径不 memorize(DB 已有)。e4 实测 4 工具收尾,质量不降。

### 根因(为什么是坑)
- **召回层 ≠ 注入层**:召回层(recall 返回命中)和注入层(SKILL/prompt 决定 agent 怎么用召回结果)是两层。召回层工作(命中了)不代表注入层会正确消费(让 agent 短路)。**只建召回不建注入指令 = 记忆被召回但被浪费。**
- **SKILL 写成固定 playbook = 流水线思维残留**(同 #12 "bug-RCA 一次走完"假设错):把 skill 当固定步骤列表,agent 忠实"走完",即使中间 recall 已给出答案也不敢跳过后续。这违背了"工具箱 + 条件分支"的 agent 范式。
- **"第一步调 recall" ≠ "命中就短路"**:前者是调用时机,后者是用结果控制流。设计时混淆了"调了 recall"和"用了 recall 的结果决定走哪条路"。
- 通病:**没核前提**("调了 recall agent 自然会短路吗?"—— 不会,除非显式教它)。

### 教训(可迁移)
1. **召回层和注入层分开设计,且注入层必须有"命中短路"的显式指令**:召回层负责把记忆找出来(已做),注入层负责让 agent 拿到命中就跳过重跑(本坑补的)。**只建召回、不写"命中怎么办" = 记忆白召回。** 短路指令要写进 SKILL 的「关键约束」+「不要」段(两边都强调),不能只写在流程描述里。
2. **skill 是工具箱 + 条件分支,不是固定流水线**(接 #12 教训):把流程写成"必走完的 7 步" → agent 忠实走完哪怕已有答案。要写成"if recall 命中 → 短路;else → 完整流程"的条件分支,明确告诉 agent**什么时候可以不走完**。
3. **验证"记忆价值闭环"要测热路径(记忆已有),不只测冷路径(首次建)**:冷路径只能证"能记";热路径才证"记了能省"。本坑就是热路径 e2e 暴露的 —— 冷路径全绿、热路径不短路。**首次调研型 skill 的价值卖点("下次秒答")必须热路径验证。**
4. **短路路径不 memorize**(DB 已有,按 id 去重虽不污染但白花步数):命中即复用,别为"走完流程"又 memorize 一遍。

### 现状(2026-08-12 定稿)
- compare SKILL + agent prompt 加「recall 优先 + 命中短路」(commit `770c97e`);onboarding 镜像同设计(recall-first 短路)。
- e4 实测:42→4 工具 / read 22→0 / memorize 2→0 / ~4min→~40s,报告质量不降(入口配对表 + 差异面 + 双源 file:line 全在,复用记忆)。
- **详见**:[compare-skill-handoff](.claude/memory/compare-skill-handoff.md)「recall 短路」段、[onboarding-skill-handoff](.claude/memory/onboarding-skill-handoff.md);关联 [[memory-design-review-2026-08-12]](召回 vs 注入层复核同类)、踩坑 #12(流水线思维)。

## 坑 #19:memory_dump 静默截断 —— `[:8000]` 吞掉一半记忆,逼 agent 13 次 recall 补捞(2026-08)

### 现象(一句话)
memory-health-check e2e(审 wpa 48 条记忆)发现:agent 反复调 `memory_recall` 13 次去补捞 dump 里"看不到"的条目 —— 根因是 `memory_dump` 把输出做 `[:8000]` 字符硬截断,**48 条只显示了 24 条**,剩下一半被静默吞掉(无任何"还有更多"的提示)。agent 发现条目数对不上,只能一条条 recall 去捞。改成 `limit/offset` 分页 + header 显式提示「showing 1-60 of N, more → memory_dump(offset=60)」后,一轮 dump 拿全,不再补捞。

### 弯路走了哪几步
1. memory_dump 初版用 `[:8000]` 字符截断控制输出大小(防一次返太多撑爆 agent context)。
2. e2e 暴露:agent 审 48 条记忆,却反复 recall 补捞 —— 因为 dump 只显示了 24 条,agent 不知道还有 24 条,只觉得"怎么缺"。
3. 初判"agent 行为异常" → 核 dump 实际返回,发现**一半条目被静默截断**,且**没有任何"还有更多"信号**。
4. 顿悟:工具静默截断 = **对 agent 撒谎**(让它以为看到的 24 条就是全部)。体检 skill 的硬约束是"审全量",静默截断直接破坏这个前提(漏看一半会误判健康度,尤其可能漏掉未决矛盾的另一半)。
5. 修法:`[:8000]` → `limit/offset` 分页(默认 60/页),header 显式提示「showing 1-60 of N, more → memory_dump(offset=60)」—— 把"还有更多"做成诚实信号,agent 知道翻页。

### 根因(为什么是坑)
- **静默截断 = 对 agent 撒谎**:`[:8000]` 砍掉内容却不告诉 agent"还有",agent 以为所见即全部 → 基于不完整数据决策。这是**工具输出的诚实性**问题,和 #5(LLM schema 不守)、#15(marshalling 脆弱)一类,都是"工具边界没防御"。但本坑更阴险:不是崩,是**静默给错数据**。
- **截断用字符数而非条目数**:8000 字符 = 约 24 条(每条溯源卡 ~330 字符),48 条正好砍半。用字符数截断对"条目完整性"是盲的 —— 可能截断在一条卡中间(撕裂),也可能整条吞掉。用 limit/offset 按条目分页才保证条目完整。
- **"防撑爆 context"的初衷对,但手段错**:控制输出大小没错,但**必须配诚实信号**(提示还有更多 + 怎么拿)。只截断不提示 = 用"省 token"换"数据正确性",划不来。

### 教训(可迁移)
1. **工具输出截断必须配诚实信号** —— 截断时要明确告诉 agent「showing X-Y of N, more → 怎么拿剩下的」(分页参数)。**静默截断 = 撒谎**,agent 会基于不完整数据决策,且不知道自己缺数据。省 token 不能以牺牲数据完整性 + 可见性为代价。
2. **按"逻辑单元"分页,不按字符数截断**:记忆按条目、代码按文件/符号、日志按行。字符数截断对逻辑单元完整性是盲的(会撕裂一条卡)。用 limit/offset 按"条目"分页,保证每个返回单元完整。
3. **体检/审计类工具的"全量"前提要工具保证**:memory-health-check 的硬约束是"审全量",那 dump 工具就必须让 agent 能拿到全量(分页可翻完),不能静默砍一半 —— 否则体检 skill 的设计前提(看全才能判健康)被工具层破坏。**工具层要支撑 skill 层的硬约束,不能背叛它。**
4. **诊断"agent 反复查同一主题"先怀疑工具静默截断/数据不全**:agent 不会无缘无故 recall 13 次,多半是它觉得"数据缺了"。先核工具实际返回了什么(是不是静默砍了),再怪 agent 行为。

### 现状(2026-08-13 定稿)
- `memory_dump` 改 `limit/offset` 分页(默认 60/页)+ header 显式翻页提示(commit `53149d8`)。SKILL.md step 1 加「注意翻页」约束(体检审全量,bump offset 直到拿完)。
- e2e 复测:一轮 dump 拿全 48 条,不再 recall 补捞。
- **详见**:[memory-health-check-handoff](.claude/memory/memory-health-check-handoff.md)「e2e 暴露+修 1 真问题」段、`src/hyperion/tools/mcp_memory.py` `memory_dump`;关联踩坑 #5/#15(工具边界防御同类,本坑是"静默给错数据"形态)。

## 坑 #20:architecture-review 草稿判断被实证推翻 —— 建议 C/D 误判短板 + A 校正方向(2026-08)

### 现象(一句话)
一份 architecture-review 草稿给 runtime/memory 提了 4 条建议(A 向量换 sqlite-vec / B 摘要 token 触发 / C 历史消息兜底 / D 记忆巩固自转),落地时**逐条调研实证**,发现其中 2 条(C、D)的"短板描述"是**基于草稿阶段的误判** —— 草稿说"consolidate 无人调"但 CLI 早 wire + recall 早 bump;草稿说"历史 synopsis 不二次压缩是短板"但 deer-flow 生产级也不二次压、 synopsis 累积靠摘要(=建议 B)。还有 1 条(A)方向需校正(sqlite-vec 默认 L2 非 cosine,建表须显式 `distance_metric=cosine`)。**4 条建议最终都落地了,但每条都经过实证校正,不是照草稿原样实现。**

### 弯路走了哪几步
1. 拿到 architecture-review 草稿,默认当"已核实的短板清单",准备逐条照做。
2. 落地建议 D 时核源码:发现草稿说"`consolidate()` 无人调"是错的 —— `cli.py:276` 早 wire 了 `hyperion memory consolidate` 命令,`recall.py:186` 早 bump access_count。**真缺口只是"recall 命中后自动触发巩固"(自转),不是"无人调"。**
3. 落地建议 C 时调研 deer-flow:发现草稿短板 2「历史 ToolMessage 不二次压缩」+ 原做法「顺手把已外置的旧 synopsis 再裁一遍」**基于误判** —— deer-flow 生产级也不二次压 synopsis(~3K < fallback 20K,到不了阈值);synopsis 累积靠 SummarizationMiddleware 整体摘要(=建议 B 已做)。**真缺口是补 `wrap_model_call` 钩子兜底历史漏网大消息(对齐 deer-flow 架构),不是二次压 synopsis。**
4. 落地建议 A 时实测 sqlite-vec:发现探针盲点 —— **sqlite-vec vec0 默认距离是 L2 不是 cosine**,记忆向量是 cosine 语义,建表必须显式 `distance_metric=cosine` + 跳零向量(零向量 cosine 未定义)。草稿只说"换 sqlite-vec",没提这个距离度量陷阱。

### 根因(为什么是坑)
- **review 草稿 = 基于读码印象的判断,不是实证**:草稿写"无人调 / 不二次压缩是短板"时,没跑 grep 核调用点、没读 deer-flow 对应实现验证。**读码印象 ≠ 实证** —— 印象会漏调用点(cli.py wire、recall bump)、会误判"该不该做"(deer-flow 也不做 = 不是短板)。
- **"短板"和"待补功能"被混为一谈**:草稿把"现象"(consolidate 在某路径没自调)当"短板"(无人调),但现象 ≠ 短板 —— consolidate 早已被 CLI + recall 调,只是缺"recall 后自动"这一个触发点。**把"缺一个触发点"夸大成"整个功能没人用" = 误判范围。**
- **"换库"建议隐藏度量陷阱**:sqlite-vec 默认 L2,记忆是 cosine —— 不核默认距离就换库,会静默退化检索质量(向量还在,但相似度排序错乱,且不报错)。同 #6(只验点名文件不验全仓)一类:**没核前提**(库的默认行为)。

### 教训(可迁移)
1. **review/设计草稿的每条判断,落地前必须实证复核** —— grep 调用点、读对标实现、跑最小探针。**读码印象会漏会错**,草稿"说有短板"不代表真有;草稿"说没人调"要 grep 验。本坑 4 条建议全落地但全经校正 —— 没一条照草稿原样实现是对的。
2. **区分"现象"和"短板"**:现象(某路径没触发)→ 补那个触发点;短板(功能缺失)→ 建功能。别把现象夸大成短板(consolidate "缺一个自转触发点" ≠ "无人调"),否则解决范围错。
3. **"对标实现"是检验"是不是真短板"的硬尺**:deer-flow 生产级也不二次压 synopsis → "不二次压"不是短板(是共识)。**对标实现做了的才可能是待补;对标实现也没做的,大概率 YAGNI(踩坑 #2 同理)。**
4. **换库/换算法先核默认行为**(同 #6 通病):sqlite-vec 默认 L2、numpy 默认行优先序…… 库的默认值常与你的语义相悖,不核就换 = 静默退化。换库的 checklist:默认距离/度量、空值处理、batch 行为、内存模型。
