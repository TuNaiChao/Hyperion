## 0. 执行摘要

| 维度 | 决策 |
|---|---|
| **引擎** | **LanceDB 嵌入式**(进程内、零 server、表=文件目录) |
| **多仓库** | **table-per-repo**(每仓库独立 LanceDB 目录,物理隔离) |
| **接口** | **VectorStore Protocol**,留 Qdrant 扩展性(P1 不实现 QdrantStore) |
| **检索** | 原生 hybrid(BM25 FTS + 向量 ANN)+ **RRF(k=60)** + 远端 reranker(DashScope `qwen3-rerank`) |
| **原子性** | LanceDB 全量重建走**目录 swap**,增量走 **merge_insert**;SQLite 图(P1.5)走 **BEGIN IMMEDIATE+WAL** |
| **版本** | `lancedb>=0.34,<0.36` 锁;`model_fingerprint` 变更触发全量重建 |
| **升级触发器** | 常驻服务 / 千万级向量 / 多用户在线 / 几百仓+亿级 → 才上 Qdrant/Milvus(**当前无一满足**) |

**一句话**:Hyperion 是 local-first 的系统软件分析 agent,向量库选 **LanceDB 嵌入式 + table-per-repo**,不上 Qdrant(运维重、优势对单用户无价值),不用纯 SQLite-BLOB(线性扫、大仓不可用)。

## 1. 候选引擎对比

| 引擎 | 形态 | ANN 算法 | 原生 hybrid | 运维 | 适合规模 | local-first |
|---|---|---|---|---|---|---|
| **LanceDB** ✅ | 嵌入式(进程内/文件) | IVF-PQ / HNSW / FTS(Tantivy) | ✅ BM25+向量+RRF+reranker | 零 server,rsync 文件 | 百万级舒适(实证 7 亿–10 亿) | ✅ |
| Qdrant | server(docker) | HNSW | ✅(稀疏+稠密) | 常驻 server,两台机各起 | 千万–亿级 | ❌ |
| SQLite + BLOB(CRG 用的) | 嵌入式 | ❌ 全表线性扫 | 自搓 FTS5+向量+RRF | 单文件 | 千万级符号以下 | ✅ |
| pgvector | 嵌入 PostgreSQL | HNSW(0.7+) | 需配 pg_trgm/FTS | 要 Postgres | 百万级 | ❌(要 DB) |
| Chroma | 嵌入式/server | HNSW | 弱(需外部) | 轻 | 百万级 | ✅ |
| Milvus | 分布式 server | 多种(IVF/HNSW/DiskANN) | ✅ | 重(K8s/etcd) | 亿级+ | ❌ |

**筛选逻辑**:
- Hyperion 是「两台机(Linux+macOS)零运维、uv+.venv」的本地工具 → **排除所有 server 形态**(Qdrant/Milvus/pgvector/Chroma-server)。
- 剩 LanceDB / SQLite-BLOB / Chroma-embedded 三个嵌入式。
- 大 C 仓(bluez/wpa/systemd 几十万行 → 几万~几十万 chunk)+ 交互式 agent 多次检索(要低延迟)→ **必须 ANN,排除 SQLite-BLOB 线性扫**。
- LanceDB 原生 hybrid+RRF+reranker 集成 > Chroma(需自搓)→ **选 LanceDB**。

---

## 2. 选型决策:LanceDB 嵌入式

5 条理由:

1. **local-first vs server**:Qdrant 要常驻 docker server,违背 Hyperion「uv+.venv+两台机零运维」理念。LanceDB 进程内、零 server,是 local-first 首选(2026 多份对比一致)。
2. **原生 hybrid**:LanceDB 自带 BM25(Tantivy FTS)+ 向量 ANN + RRF 融合 + reranker 接口,**不用自搓胶水**(对比 CRG 自搓 FTS5+Python cosine+RRF)。
3. **规模舒适区**:百万级 chunk 是 LanceDB 舒适区(生产实证 7 亿–10 亿向量),Qdrant 在此量级优势不显。10 个系统仓库 ≈ 100 万 chunk,远未到瓶颈。
4. **两台机协作**:LanceDB 表 = 文件目录(`data/code_index/`),随数据 rsync 跨机一致;Qdrant 要两台机各起 server。
5. **Qdrant 优势对 Hyperion 无价值**:富 payload 过滤(单机可忽略)、多租户 shard(非多租户)、client-server 高并发(单用户)——这些都是 SaaS 场景的优势,本地工具用不上。

---

## 3. 多仓库:table-per-repo

未来扩展到 systemd / pipewire / wpa_supplicant 等多仓库,**不上 Qdrant/Milvus**,走 LanceDB table-per-repo(LanceDB 多租户最佳实践:每表 = 独立 Lance 文件目录,物理隔离天然免费):

```
data/code_index/
├── bluez/lancedb/          # 每仓库一张表:独立 index / manifest / 增量 / IVF-PQ
├── systemd/lancedb/
├── pipewire/lancedb/
└── wpa_supplicant/lancedb/
```

- **单库搜**:选表查(`store.hybrid_search(repo, ...)`)。
- **跨库搜**:并行查多表 → 应用层 RRF 合并(P1.5+ 按需)。
- **文件级独立**:某仓库索引可单独 rsync / 删除 / 重建,互不影响。

## 4. VectorStore 接口(留 Qdrant 扩展性)

按 Hyperion provider 抽象哲学(模型工厂 / Embedder / Reranker),`store.py` 抽象 `VectorStore` 接口,底层默认 LanceDB,**接口不锁死 LanceDB 专属 API**:

```python
class VectorStore(Protocol):
    def upsert(self, repo: str, chunks: list[CodeChunk], vectors: np.ndarray) -> None: ...
    def hybrid_search(self, repo: str, query_vec: np.ndarray, fts_query: str,
                      limit: int, where: str | None = None) -> list[dict]: ...
```

- 默认实现 `LanceDBStore`(table-per-repo)。
- **未来若触发升级(见 §10)**,加 `QdrantStore` 实现,config 一行切,上层 `retrieval.py` 不改。
- **P1 不实现 QdrantStore**——只保证接口留口子,不现在上(避免过度工程)。

## 5. schema 设计(`store.py`)

- **pyarrow schema**(生产优于 pydantic LanceModel:零类型转换开销、多进程 spawn 后可直接序列化)。
- **非向量列**(`CODE_FIELDS`):id / symbol / kind / file / language / start_line / end_line / text / content_hash / fts_text。
- **向量列**:`pa.list_(pa.float32(), dim)`,**维度建表时定死**(改维度 = 新建表迁移,由 `model_fingerprint` 检测触发)。
- **两个必需索引**(LanceDB 0.34 新 API `create_index(config=...)`,旧 `create_scalar/fts_index` 已弃用):
  - `create_index("id", config=BTree())` —— **merge_insert 必须**,否则撞 "unindexed rows > 10000"。
  - `create_index("fts_text", config=FTS(with_position=True, stem=False, remove_stop_words=False, ascii_folding=True))` —— **代码场景关键参数**:`stem=False`(否则 malloc 被 stem)、`remove_stop_words=False`(否则 int/void/public/return 被当停用词删掉)。
- **metric**:向量已 L2 归一化 → `dot`(最快);建 IVF 时定 `metric="dot"`。
- **fts_text 预拆词**:LanceDB 默认 `simple` tokenizer 不拆下划线(`hci_inquiry_complete` 是一整个 token),chunker 层把 snake/camel/SCREAMING 预拆成词袋。

## 6. 原子性

LanceDB **无事务**(不像 SQLite),写入不是跨批次原子的。按操作类型分两条路:

**① LanceDB 向量库**:
- **全量重建**(`index build`):先写 temp 目录 `data/code_index/<repo>/lancedb_tmp`,全部成功后 `os.rename` 原子切成 `lancedb`(同文件系统 rename 是原子 syscall),失败丢弃 tmp——要么旧索引、要么新索引,无半成品。
- **增量**:``merge_insert("id").when_matched_update_all(where="target.content_hash <> source.content_hash").when_not_matched_insert_all()`` —— 条件 upsert,只重写 content_hash 变了的行,**批级原子**,不需 temp。消失路径用 `when_not_matched_by_source_delete` 清孤儿。

**② SQLite code_graph(P1.5,有事务)** —— 借鉴 code-review-graph `graph.py`(9 个 schema 版本验证):
- 连接三件套:`isolation_level=None` + `journal_mode=WAL`(读写并发)+ `busy_timeout=5000`。
- 每文件/每批一个 `BEGIN IMMEDIATE` 事务(删旧+插新原子化),`_begin_immediate` 嵌套防御(先 rollback 脏事务再 BEGIN)。
- **抛弃图层面的 temp+rename**——CRG 方案更简更稳、增量友好、长重建期间可读(WAL 快照)。

## 7. 混合检索(`retrieval.py`)

**两阶段架构**(十年工业标准):bi-encoder 召回 → cross-encoder 精排。

**Stage 1 — hybrid 召回(LanceDB 原生)**:
```python
tbl.search(query_type="hybrid", vector_column_name="vector", fts_columns="fts_text")
   .vector(qvec).text(query).limit(candidate_top_n=50)
   .rerank(RRFReranker(K=60, return_score="relevance"))   # RRF 融合 BM25+向量
```
- **BM25(FTS)**:对 C 的函数名/宏名/错误码(强词法信号)召回好。
- **向量**:语义相似(如「断连处理」↔ `disconnect_cb`)。
- **RRF(k=60)**:Cormack 2009 标准,rank-based 不需归一化,客户端算。
- dense 和 sparse **失败模式正交**(改名 dense 强、错误串 BM25 强)→ 必须混合。

**Stage 2 — cross-encoder 精排(reranker provider 抽象)**:
- 默认**远端** DashScope `qwen3-rerank`(同 `DASHSCOPE_API_KEY`、¥0.0005/千token≈8万查询=¥1、OpenAI 兼容 `/reranks`)。
- SiliconFlow `BAAI/bge-reranker-v2-m3` **免费** fallback;本地仅 GPU 可选(CPU 257s/100doc 不可交互)。
- 对 hybrid 返回的 top-50 候选的 **fts_text**(短)打分,取 top-5。

**补强(借鉴 CRG search.py)**:`_out_mode` 可观测(记录走了 hybrid/fts/semantic/keyword/none)+ 查询类型 boosting(PascalCase→Class、snake→Function、dotted→qualified)+ 三级降级。

**⚠️ weakest-link 警示**([Balancing the Blend, arXiv 2508.01405, 2025-08](https://arxiv.org/html/2508.01405v2)):RRF 不是越多路越好,弱路径污染融合。**加 BGE-M3 sparse/SPLADE 第 3 路前必须单路 eval 消融**。

## 8. 版本管理

- **`lancedb>=0.34,<0.36`** 锁(pyproject):0.34 的 hybrid/Reranker API 已 live 核实;锁上限避破坏性变更。
- **`model_fingerprint`**(`provider|model|base_url|dim|normalize`):进 `index_manifest.json`,任一项变 → 全量重嵌(向量空间变了)。
- **`schema_version`**:chunk schema 改 → 全量重建。
- **`index_manifest.json`**(LanceDB sidecar,建库成功后落盘,检索前校验):`repo_commit` / `model_fingerprint` / `schema_version` / `file_manifest{路径: content_hash}`。

## 9. 与 CRG(纯 SQLite-BLOB)的对比 · 为什么不照搬

> 详见 [code-review-graph-调研与借鉴.md §6](code-review-graph-调研与借鉴.md)。

| 维度 | CRG(纯 SQLite+BLOB) | Hyperion(LanceDB) |
|---|---|---|
| 向量检索 | **O(N) 全表扫 + Python cosine** | **O(log N) IVF/HNSW ANN** |
| 大仓(几万~几十万 chunk) | 单查询几秒,交互不可用 | 亚秒级 |
| 取向 | code review 省 token(符号级,中小仓) | Bug 定位/深度研究(大 C 仓,多次检索,低延迟) |
| hybrid | 自搓 FTS5+向量+RRF+降级 | 原生 hybrid+RRF+reranker(少造轮子) |

**结论**:CRG 的向量层是为「中小仓 code review」做的取舍(线性扫换简化),不适合 Hyperion。**向量库保持 LanceDB**;CRG 值得抄的是 **SQLite 图层**(P1.5)+ 工程惯例,不是向量存储。

## 10. 升级触发器(何时才真该上 Qdrant/Milvus)

任一满足才重新评估(**当前一个都不满足**):

| 触发条件 | 该上 |
|---|---|
| Hyperion 变成**常驻后台 agent 服务**(规避嵌入式长驻内存泄漏) | Qdrant server |
| 单库向量到**千万级**(≈几亿行代码) | Milvus 分布式 |
| **多用户并发在线查询**(SaaS) | Qdrant client-server |
| 仓库数到**几百 + 亿级向量** | Milvus |

未触发前,LanceDB 嵌入式 + table-per-repo 是教科书最优。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| LanceDB FTS 对 C 标识符召回弱 | `fts_text` 预拆词(snake/camel/SCREAMING);不足则 `rank_bm25` 二级精排 |
| embedding 模型锁定后想换 | `model_fingerprint` 检测 → 变更触发全量重建 |
| 全量索引慢(几十万行 CPU embed 几十分钟) | 默认远端 DashScope embedding(免本地推理)+ 增量(merge_insert 只重嵌变化)+ 进度打印 |
| LanceDB 运行时兼容(ABI/glibc/tantivy) | wheel 覆盖 cp39-abi3(含 3.12)+ macOS arm64,无需编译;`setup.sh` 加 `import lancedb` 冒烟测 |
| 单写者并发 | LanceDB 单写者模型;多进程 `spawn` 非 `fork`;index.py 写入串行(即使解析并行) |
| 增量孤儿(改名/移动) | `when_not_matched_by_source_delete` 清孤儿;或 `git diff --name-status` 的 `R` 显式搬运 |
