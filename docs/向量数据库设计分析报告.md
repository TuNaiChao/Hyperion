## 0. 执行摘要

`architecture.md` 在代码理解与记忆层对向量检索的运用具备扎实的混合检索（BM25 + Dense + RRF）设计思路。然而，深入分析发现其在**存储收敛**、**多租户隔离**、**检索权重动态性**、**代码拓扑感知**以及**嵌入模型演进**五个维度存在系统性优化空间。

本建议书结合 2025—2026 年 Qdrant、Pgvector 社区最佳实践及向量检索领域（SIGIR/ICLR）最新工程方法论，提出 7 大优化方向及分阶段实施路线图，旨在将向量检索从“可用”提升至“生产级高可用、高召回、可演进”。


## 1. 现状与核心痛点

| 维度           | 现状（来自 `architecture.md`）                               | 生产环境隐患                                        |
| :------------- | :----------------------------------------------------------- | :-------------------------------------------------- |
| **存储碎片化** | LanceDB（代码索引）、LangGraph Store/pgvector（记忆）、Graphiti/FalkorDB（时序图谱）各自为政 | 运维地狱（3 套监控/备份/扩容）；事务一致性难保证    |
| **多租户隔离** | 仅通过 `namespace` 或 `component` 字符串做逻辑区分           | 大租户（如 bluez）与小租户争抢资源，无物理/性能隔离 |
| **检索权重**   | 固定 RRF 融合（`k=60`），无查询意图感知                      | 精确错误码查询与自然语言查询共用一套权重，互相稀释  |
| **拓扑感知**   | 纯文本/符号匹配（`grep_symbol`），无调用链图遍历             | 无法处理“病在 A，根因在调用链上游 B”的跨函数定位    |
| **模型升级**   | 承认“嵌入模型换需全量重嵌”为技术债务                         | 未来模型升级将导致长时间服务中断或全量离线计算      |


## 2. 优化建议

### 2.1 存储收敛：确立 Qdrant 为唯一生产向量引擎

**原则**：向量数据库不是“谁都能开一个”的附属组件，而应作为平台级原子能力（VectorStore Provider）统一供给。

| 组件              | 现状存储                        | 优化后存储                           | 职责调整                                                     |
| :---------------- | :------------------------------ | :----------------------------------- | :----------------------------------------------------------- |
| **代码索引**      | LanceDB（本地）→ Qdrant（生产） | **Qdrant**（唯一生产）               | 存函数/宏/结构体的 Dense + Sparse 向量                       |
| **记忆基座**      | LangGraph Store（pgvector）     | **Qdrant** + PG（纯 KV）             | 向量存 Qdrant；PG 仅存元数据（时间戳、来源、置信度）         |
| **Graphiti 图谱** | FalkorDB（含向量）              | **FalkorDB（纯图）+ Qdrant（向量）** | 图结构存 FalkorDB，实体 Embedding 剥离至 Qdrant（`graphiti_entities` Collection） |

**关于 pgvector 的审慎决策依据**：根据 Qdrant 团队对 110+ 生产社区的调研，pgvector 需同时满足“向量 < 100万、无预过滤、无混合检索、低频写入”等条件才能良好运行。本项目代码索引预估远超百万级，且明确依赖 BM25 混合检索与高频写入（持续学习），**pgvector 不适合作为本项目生产向量库**，仅可作为开发测试环境的轻量替代。


### 2.2 多租户策略：Qdrant 分层多租户（Tiered Multitenancy）

Qdrant 1.16+ 引入了分层多租户机制，完美适配本项目的多组件（bluez/wpa）、多版本（5.x/6.x）场景。

**推荐策略**：

```
Collection: code_embeddings (主集合)
├── Fallback Shard (默认共享区)
│   └── 存放所有小租户（如 bluez 历史版本、实验性分支）
├── Dedicated Shard: tenant_bluez_main
│   └── BlueZ 主分支（大租户，独占资源）
├── Dedicated Shard: tenant_wpa_main
│   └── wpa_supplicant 主分支（大租户，独占资源）
└── Dedicated Shard: tenant_bluez_v5
    └── BlueZ 5.x LTS 版本（独立物理隔离）
```

**实施要点**：
- 使用 Qdrant 的 **Tenant Promotion** 机制：当某组件向量数超过阈值（如 50万）时，自动从 Fallback Shard 提升至 Dedicated Shard。
- 每个 Shard 独立配置 HNSW 参数与内存配额，大租户可分配更多资源。


### 2.3 混合检索升级：从静态 RRF 到意图感知自适应融合

当前固定 `k=60` 的 RRF 融合无法适配不同查询类型。引入 **Triage 节点的轻量级意图分类器**（规则 + 本地 Qwen3），动态调整 BM25 与 Dense 权重。

| 查询类型   | 判别特征（正则/规则）               | BM25 权重 | Dense 权重 | RRF k      | 说明           |
| :--------- | :---------------------------------- | :-------- | :--------- | :--------- | :------------- |
| **精确型** | 含 `0x[0-9A-F]+`、`ERR_*`、全大写宏 | **2.0**   | 0.5        | 30         | 强符号匹配优先 |
| **语义型** | 无代码符号，纯自然语言              | 0.6       | **1.8**    | 60         | 语义泛化优先   |
| **混合型** | 既有自然语言又有符号引用            | 1.0       | 1.0        | 60（默认） | 等权融合       |

> Qdrant 的 `prefetch` + `fusion` API 支持在查询时透传不同检索器的权重，无需重建索引。

**高性能捷径**：若 BM25 原始检索的 Top-3 得分 > 30（高置信度精确匹配），则**直接返回 BM25 结果，跳过 BGE-Reranker**。`bge-reranker-v2-m3` 为 Cross-Encoder（单次 50-100ms），此捷径在高并发下可节省约 60% 的 Rerank 计算开销。


### 2.4 拓扑感知检索：调用链图增强补盲

纯向量检索无法捕捉调用链拓扑关系。引入 **两阶段检索架构**：

| 阶段                  | 操作                                                      | 数据源                        |
| :-------------------- | :-------------------------------------------------------- | :---------------------------- |
| **Phase 1：种子召回** | 向量/BM25 检索获取初始候选函数集合（Top-20）              | Qdrant（向量索引）            |
| **Phase 2：图扩散**   | 以种子函数为中心，在调用图中做 ±1~±2 跳游走，收集邻居函数 | FalkorDB + ctags 预计算调用图 |
| **Phase 3：融合排序** | 种子 + 邻居重新做 RRF 融合，输出 Top-5                    | 应用层                        |

**向量存储配合**：在 Qdrant Payload 中预存该函数的 `callers` 和 `callees` 符号名列表，供 Phase 2 快速查找，避免频繁查询图数据库。


### 2.5 嵌入模型版本管理：蓝绿迁移与零停机升级

规避“全量重嵌导致服务不可用”风险，采用工业界成熟的蓝绿迁移策略：

| 阶段              | 操作                                               | 服务状态      | 流量分配 |
| :---------------- | :------------------------------------------------- | :------------ | :------- |
| **Phase 1：扩展** | 在 Qdrant 新建 `code_emb_v2` Collection，保留 `v1` | 正常（读 v1） | 0%       |
| **Phase 2：回填** | 后台异步 Worker 将全部数据用新模型重嵌写入 `v2`    | 正常（读 v1） | 0%       |
| **Phase 3：灰度** | 网关层按比例（1%→10%→50%）将读流量切至 `v2`        | 正常（双读）  | 逐步切流 |
| **Phase 4：全量** | 100% 切至 `v2`，下线 `v1` Collection               | 正常（读 v2） | 100%     |

**版本元数据设计**（Payload 字段）：
```json
{
  "embedding_model": "voyage-code-3",
  "model_version": "20250701",
  "embedding_dims": 1536,
  "generated_at": 1700000000
}
```
Recall 节点检索时，根据当前配置的模型名，通过 Qdrant `filter` 仅查询对应版本的向量，避免跨版本向量空间不一致导致相似度失真。


### 2.6 索引调参与内存优化

| 优化项                        | 推荐配置（代码检索场景）          | 依据                     |
| :---------------------------- | :-------------------------------- | :----------------------- |
| **HNSW `m`**                  | 32–64（默认 16）                  | 提高召回率，内存换精度   |
| **HNSW `ef_construction`**    | 200–400（默认 100）               | 建索引稍慢，查询质量提升 |
| **查询 `ef`**                 | 50–100（默认 10）                 | 扩大搜索范围             |
| **Binary Quantization（BQ）** | 启用（内存降 90%，召回损失 < 5%） | Qdrant 生产标配          |
| **热/冷数据分离**             | `on_disk` 存储 + RAM 缓存热分片   | 控制内存爆炸             |

**元数据过滤性能**：为 Payload 中所有过滤字段（`component`、`version`、`symbol_type`、`file_path`）建立**独立 Payload 索引**，使 Qdrant 在执行带过滤的向量搜索时可采用 **Filterable HNSW**（遍历时同时应用过滤），避免低效的“先搜后滤”。


### 2.7 可观测性与检索质量看板

向量检索不能黑盒运行，必须建立以下指标监控：

| 指标类别     | 具体指标                         | 告警阈值     | 采集方式                         |
| :----------- | :------------------------------- | :----------- | :------------------------------- |
| **性能**     | P99 检索延迟                     | > 500ms      | Qdrant Metrics / 应用埋点        |
| **质量**     | 召回率（Recall@10）              | < 90%        | 离线评估集定期测算               |
| **资源**     | 内存使用率、索引构建耗时         | > 80% / > 1h | Qdrant Metrics                   |
| **过滤效率** | 过滤选择性（过滤后剩余向量比例） | < 1%         | 应用层记录（需关注查询是否过窄） |

**可解释性**：在检索结果的 Payload 中附加召回路径元信息（BM25 排名 / Dense 排名 / 最终融合得分），供开发人员调试。

## 4. 总结

`architecture.md` 对向量检索的定位在学术层面（混合检索、RRF、重排）是先进的，但在**生产工程化**层面存在明显缺口：

> **核心矛盾**：“代码索引”与“记忆”在逻辑上需要隔离，但在存储层面过度解耦，导致向量碎片化。而固定 RRF 权重与缺失的拓扑感知，则限制了检索质量的上限。

**核心理念**：向量数据库不是“存进去就能用”的黑盒附件，而是需要**存储收敛、多租户规划、权重自适应、图拓扑补盲、模型版本管理、索引调优、可观测性**七位一体工程化思维的平台级能力。建议团队优先攻克 **P0 存储收敛**与 **P1 自适应融合**，为后续高阶优化奠定坚实基础。
