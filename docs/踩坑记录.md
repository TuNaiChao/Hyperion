# 踩坑记录(Pitfall Log)

> 本文档专门记录 Hyperion 项目设计/实现中走过的**弯路**、踩过的**坑**,以及背后的**根因**和**教训**。
> 每条 = 一个坑,固定五段:**现象 → 弯路走了哪几步 → 根因 → 教训(可迁移)→ 现状**。
>
> **目的**:把"反应式打补丁"变成"前置认知",避免重复踩同一个坑。新坑往上加(序号递增)。
>
> **写入时机**:做了设计反转 / 删了已建的代码 / 用户指出过度设计 / 调研推翻既有方案 / 踩了库或模型的非显然坑 时。
>
> 配套:具体设计真相看 `docs/设计/`;决策记忆看 `.claude/memory/`。本文是"**为什么这么决策**的反面教材汇总"。

## 坑 #1:patch 投票 rerank —— 一次三段反转的弯路(2026-07)

### 现象(一句话)
为 bug-RCA 设计了 Agentless 式「多候选补丁 + majority voting」rerank 机制,经历 **当主路径 → 降级为默认关兜底 → 整体移除** 三步反转,最终全删。净效果:白建了一整套(`rerank.py` + config + state + test + 三处复用规划 A/B/C),又全拆掉。

### 弯路走了哪几步(三次认知更新)
1. **初版(当成主路径)**:照搬 Agentless「②repair 采 N 候选 → ③verify 选 top-1(majority voting)」,甚至提前排了 **A/B/C 三处复用**(A=localize 文件投票 / B=深度调研事实一致性 / C=有 oracle 的 patch),觉得这套「采 N 个 → 归一化 → 投票」原语很值钱,得多处复用才回本。
2. **第一次反转(#54-rework → B,2026-07-30)**:意识到 wpa/bluez **无测试套件** + glm-5.2 **近确定性** → N 个补丁几乎一样 → 投票平凡 + N× token 白烧。主路径改**迭代 verify-refine(B)**(同 opencode 会话双循环 + verdict 自审 + `validate_patch` 执行门控),rerank "降级为默认关的兜底"。
3. **第二次反转(整体移除,2026-07-31)**:连"默认关兜底"也删了。导火索是准备上 **localize 文件投票(A)** 时,用户质疑"这是不是过度设计 / 白烧 token"。深度调研(OpenHands/Aider/R2E-Gym/Agentless 原文)坐实:① 投票只在有 oracle 时有效;② 现代 SOTA 已转单轨迹+执行验证。→ `rerank.py` 整文件 + `_rerank_fallback` + `RerankConfig` + `delegate.rerank` + state 两字段 + 测试,全删。

### 根因(为什么是坑)
- **投票有效的前提没在设计前就想清楚**:它有效需(二选一)① 廉价可靠 **oracle**(测试/repro);② 样本**多样 + 可归一化到同一规范解**(self-consistency)。**Agentless 投票原文就是 "majority voting after test filtering"** —— filter+vote 的命门是测试当裁判。wpa/bluez 既无测试、模型又近确定性,**两条都不沾 → 投票必然平凡**。这个前提本该在动手写 `rerank.py` 前就问清楚。
- **"默认关兜底"是伪安全**:留一个永不开启的开关,既增加 config/state/test/文档的维护面,又给架构故事添噪(读者要问"这开关啥时候开?"),还不提供真实逃生口(没 oracle 时开了也没用)。**死代码不是保险,是债。**
- **没跟上趋势**:2025-2026 SOTA —— OpenHands(critic 模型 + 执行反馈)、Aider(单轨迹 + lint/test 每步)、R2E-Gym(执行式验证 > 无执行)—— **已弃文本相似度投票**,转单轨迹 + 执行信号验证。我们的 B verify-refine 正是这条路,rerank 是逆趋势的遗留。
- **"原语值钱得多处复用"的执念**:为分摊设计成本,提前规划 A/B/C 三处复用,反而让一个该删的东西显得"动不得"。复用是结果,不是理由。

### 教训(可迁移到别的坑)
1. **上多采样/投票前先问两个问题**:「这有 oracle 吗?样本会真多样吗?」两否 → 别上,走迭代 refine。没有裁判的投票是安慰剂。
2. **别留"默认关"的死代码兜底** —— 要么它有用(默认开),要么删。YAGNI:不为投机未来扛死代码。真到那天,算法 ~40 行、git 史可查,重写比维护一个语义模糊的开关便宜。
3. **区分两个 "rerank",别误伤**:① patch **多数投票**(Agentless 式,本坑,已删);② **检索 cross-encoder 重排**(BM25→精排召回块,标准 IR 技术,默认开、有效)。砍 (a) 时差点因为名字一样误伤 (b)。
4. **用户对复杂度的直觉通常对** —— 当用户说"这是不是过度设计",往往是。该认真调研验证,而不是为已有代码辩护。
5. **设计前先查前提条件**(本仓有没有测试套件?模型确不确定?),别等建完了跑不通才发现前提不成立。

### 现状(2026-07-31 定稿)
- **全删**:`rerank.py`(整文件)、`nodes._rerank_fallback`、`RerankConfig` + `delegate.rerank` 配置、state `candidates`/`rerank_summary`、rerank fallback 测试。ruff 全过、pytest 46 passed。
- **保留**:检索 rerank(`memory.native.rerank` cross-encoder)+ B verify-refine(单轨迹迭代 + `validate_patch` 执行硬门控)。
- **未来**:真有 oracle(hwsim/bluez 测试套件就绪 / #50 repro 落地)再按 Agentless filter+vote 重写,**不预建**。
- **详见**:`docs/设计/bug-rca-design.md` §7.6(设计真相)、`.claude/memory/rerank-mechanism-where-it-shines.md`(决策记忆)。

## 坑 #2:Hyperion 侧定位漏斗 —— 建到一半发现与 opencode 重复(2026-07)

### 现象(一句话)
为 bug-RCA 设计 + 起建了一套 Hyperion 自有的 Agentless 式定位漏斗(file→function→line)+ 关键字抽取(regex)+ 方案A 检索预筛(固定管线阶段),结果发现这**与委托目标 opencode 自己的定位能力重复**(double localization),整套砍掉,改成"opencode 自主定位 + Hyperion 把差异化能力做成 MCP 工具给它调"。

### 弯路走了哪几步
1. **初版(把 Agentless 漏斗搬进 Hyperion)**:照搬 Agentless「分层定位 file→function→line」作为**委托前**的固定预筛管线,外加 trigger_parser(regex 抽关键字)+ 方案A(code_index 检索取 top-N 文件喂漏斗)。认为"委托前组装手术刀级上下文"就是 Hyperion 的核心价值,所以这套漏斗得自己建。
2. **起建 + 设计**:建了 trigger_parser 雏形(parse_issue + regex `extract_keywords` + `filter_log_window`);设计并展示了方案A 漏斗代码(检索预筛 → 缩树喂 LLM pick)。
3. **用户质疑 + 三轮调研反转**:用户问"opencode 本来定位能力就很强,加这么多是不是冗余?只调度 + 提供工具是不是更好?"。三轮调研(全流程体检 / agentic RAG / opencode 能力核实)坐实:① 漏斗与 opencode **双重定位**;② 2026 主流是"lead agent + 工具"(deer-flow 2.0 自己都从固定 planner/reporter 图迁到单 SuperAgent + `task` 工具;Claude Code/OpenHands 同款);③ opencode **原生支持** mid-session 调 MCP 工具 → Hyperion 把 recall/search_codebase/filter_logs 做成工具给 opencode 调即可,不必自跑漏斗。→ 整套漏斗砍,改工具驱动委托。

### 根因(为什么是坑)
- **前提没查清(同 #1 rerank)**:建漏斗前没问"**委托目标 opencode 是不是已经会定位?**"——它是强 coding agent,定位本就是其强项。Hyperion 再跑一套 = 重复劳动(double localization,白花一套漏斗的 token/时间)。和 #1"没 oracle 投票平凡"同病:**设计前没核前提**。
- **误搬 Agentless**:Agentless 是**独立 agent**(没有另一个 coding delegate 帮它定位),它的漏斗是"自己定位自己修"。Hyperion 是**委托型**(把活派给 opencode),再在前面套漏斗 = 两个 agent 干同一件事。"Agentless 固定漏斗便宜 ~6×"的教训**仍成立**,但落到"工具内部"(`search_codebase` 工具内部跑廉价检索回手术级锚点),而非"Hyperion 的重复管线"。
- **价值定位偏差**:把"Hyperion 的价值 = 委托前预筛漏斗"想窄了。真正的护城河是 opencode **缺/搞不便宜**的:记忆(跨会话)、code_index 廉价检索、日志过滤 —— 这些做**工具**才有价值,重造定位漏斗没价值。
- **regex 抽关键字逆趋势**:2026 主流是"LLM 自己抽 / agentic 检索"(Claude Code 已弃向量库改 agentic search);regex 抽是偏老派做法,且实测在日志上失败(代码符号 ≠ 日志散文形)。

### 教训(可迁移)
1. **建任何 Hyperion 侧能力前先问:委托目标(opencode)是不是已经会这个?** 会 → 别重复,把 Hyperion **独有的**(opencode 缺的)做成工具给它调。和 [[avoid-overengineering]] 的"查前提条件"一脉相承。
2. **委托型 agent 不建平行管线,建能力工具**:lead agent + 工具 + 调度 + 验证/报告(2026 共识:deer-flow 2.0 / Claude Code / OpenHands)。"工具 > 固定流程"——但**固定/廉价的检索活在工具内部**(search_codebase 内部跑固定 BM25+rerank),控制流是工具驱动。
3. **借鉴要分清"独立 agent"还是"委托型"**:Agentless(独立)的漏斗 ≠ Hyperion(委托型)该建的;搬之前对齐架构形态。
4. **用户对冗余的直觉又对了**(同 #1 rerank)——"是不是加太多了"往往是。该认真调研验证,而非为已建代码辩护。
5. **多轮调研在重度实现前拦住了**:这次只建了 trigger_parser 雏形 + 设计了方案A(没全量接线+测试),损失比 #1 rerank(已全建+测试+三处复用规划)小。**设计阶段调研比实现后反转便宜**。

### 现状(2026-07-31 定稿)
- **砍**:Hyperion 侧定位漏斗(file→function→line)、recall/localize/assemble_localize 三独立节点、方案A 作固定预筛阶段、regex extract_keywords。bug-RCA 流程简化为五步:ingest→delegate_localize_loop(opencode 自定位+MCP 工具)→assemble_repair→delegate_repair_loop→report_memorize。
- **改工具**:recall / search_codebase / filter_logs 三能力做 MCP 工具(`hyperion mcp serve`),opencode 经 MCP 按需调,agent prompt 提示优先用(防它裸 grep 烧 token)。
- **代码状态**:文档已全量对齐(docs/设计 6 份已审改);**代码尚未重构**(graph.py 仍 8 节点、localize.py 仍漏斗)——文档领先代码,refactor 记 backlog(见 bug-rca-design.md §9)。
- **详见**:`docs/设计/bug-rca-design.md` §1/§2/§6(设计真相)。

## 坑 #3:delegate 子进程流式读 readline 64KB 行长崩(2026-08)

### 现象(一句话)
R3.1 e2e(`hyperion bug-rca --log <2.6MB 日志>`)早期崩在 `Separator is not found, and chunk exceed the limit` —— opencode `--format json` 事件流里出现 >64KB 的单行(读大文件/大日志的工具结果嵌在一条 JSON 里),delegate 的 `_drain` 用 `async for line in stream` 直接抛 ValueError,整个 run 挂。

### 弯路走了哪几步
1. **初判 R3.1 改动引入**:先怀疑是新加的 MCP 工具 / 砍漏斗有 bug;看栈发现挂在 asyncio 子进程流读取层,跟 R3.1 逻辑无关。
2. **定位 readline 隐式限制**:`async for line in stream` 走 `StreamReader.readline()`,默认 `limit=2**16`(64KB);单行超限**不截断、不等待,直接 ValueError**。
3. **为何 R2 没踩到**:R2 没 `--log`,opencode 只读代码文件(<64KB 居多);R3.1 加了大日志 + filter_logs,opencode 读 2.6MB 日志(或 ~150KB 的 `scan.c`)→ 单条事件 >64KB → 崩。

### 根因(为什么是坑)
- **子进程 stdout 用 readline 读是脆的**:opencode/grep/cat 等 JSON 事件流单条可能很大(文件内容嵌事件里),readline 的 64KB 行长限是**隐式的**——平时不报错,超大行直接崩,没有中间地带。
- R3.0 #56 流式改造选了 `async for line in stream`("逐行流式读"的直观写法),没考虑**单行无上限**的场景。
- 通病同 #1/#2:**没核前提**(readline 的行长限)就用了 API。

### 教训(可迁移)
1. **子进程流式读 stdout 别用 `async for line in stream` / readline**(隐式 64KB 行长限)——改 `read(n)` 块读 + 之后统一 `splitlines()`,行长无上限。
2. delegate 这种"聚全量再 `_parse_stream`"的场景,块读**等价于** readline(反正 EOF 后才解析),没有损失;只有真要"边读边增量处理"才需要按行,而那也该自己缓冲 split。
3. **大输出工具结果要双防**:防流崩(块读)+ 防上下文污染(工具内部封顶 `max_lines` + prompt 禁裸读大文件,见 `filter_logs` 的 400 行上限 + localize prompt 的"禁直接 read 大日志,只调 hyperion_filter_logs")。

### 现状(2026-08-03 定稿)
- `_drain` 改 `while True: chunk = await stream.read(65536)`(块读,行长无上限);e2e 不再早期崩。
- localize prompt 强化"禁直接 read 大日志,只调 `hyperion_filter_logs`"(防模型裸读撑爆上下文)。
- **详见**:`src/hyperion/tools/delegate.py` `_drain`;关联 opencode MCP 接线硬细节(`.claude/memory/opencode-mcp-wiring.md`,含 listTools 5s 超时 / <8KB pipe / PYTHONUNBUFFERED 等同源坑)。

## 坑 #4:被外部进程拉起的服务,相对路径按"调用方 cwd"解析(2026-08)

### 现象(一句话)
R3.1 e2e 产了报告但 `verified:False`、没写 `.patch`;查 `workspace/code` 的 `git diff --cached` 发现有**正确的 .c 改动**(events.c + dbus_new_handlers.c)却混入 `data/memory/memory.db` + `data/code_index/wpa/lancedb/*` 噪声 → `validate_patch` apply --check 挂。

### 弯路走了哪几步
1. 先疑**模型没改码**:git diff --stat(未带 --cached)只见 memory.db,以为 opencode 没动手;后查 events.c 发现已加守卫 —— 是看错了暂存/未暂存。
2. 再疑 **quilt 工作区**(opencode 自己提到 `.pc/` + `series`,以为补丁走 quilt 层 git 看不到)。
3. 最后 `git diff --cached` 才定位噪声源:`hyperion mcp serve`(被 opencode 拉起)把 `data/memory` + `data/code_index` 写进了 `workspace/code/data/`。

### 根因(为什么是坑)
- **opencode 把 MCP server 的 cwd 设成 workspace/code**(`InstanceState.directory`);而 Hyperion config 里 `data/` 路径是**相对的**(`store_path: data/memory`、LanceDB `data/code_index`)→ 按 MCP server 的 cwd 解析成 `workspace/code/data/`。
- 双重后果:① `git add -A` 把这些 data 文件连带暂存 → 补丁脏 → apply --check 挂;② 记忆/索引写到**临时 workspace 库**,不持久(recall 查空、跨 bug 不共享)。
- 通病:**没核前提**("被外部进程拉起时,cwd 还是不是 Hyperion 根")。CLI 自己跑时 cwd=Hyperion 根,相对路径对;被 opencode spawn 时 cwd 变了,相对路径全错位。

### 教训(可迁移)
1. **被外部进程拉起的服务,其相对路径默认按"调用方 cwd"解析** —— 要么 chdir 回自家根,要么 config 路径绝对化(锚到包/配置文件位置)。
2. Hyperion 侧选了前者(`cmd_mcp` 在 `build_server` 前 `os.chdir(Hyperion 根)`):MCP server 是独立进程,工具都用绝对路径/表名(log_path 绝对、codebase 走 env、index 走 repo 名),不依赖 cwd,chdir 无副作用。
3. **诊断补丁问题时,务必看 `git diff --cached`(暂存区)而非 `git diff`**(后者只看未暂存;_observe_patch 用 add -A + diff --cached)。

### 现状(2026-08-03 定稿)
- `cmd_mcp` chdir 到 `_default_config_path().parent.parent`(Hyperion 根);MCP server 的 memory/code_index 路径解析回正轨,补丁干净、记忆持久。
- **详见**:`src/hyperion/cli.py` `cmd_mcp`;`opencode-mcp-wiring` 记忆(同根坑)。

## 坑 #5:workflow 盲信 LLM 结构化输出的 schema(2026-08)

### 现象(一句话)
R3.1 e2e #2 崩在 `1 validation error for Evidence / line / Input should be a valid integer ... input_value='3067,4105,5980,8452,9818,10326,10682'` —— glm-5.2 的 `evidence[].line` 给了**逗号多行串**而非单个 int,`node_report_memorize` 直接 `Evidence(line=<串>)` → pydantic 崩 → 整个 bug-rca 崩。

### 弯路走了哪几步
1. e2e #1 同一处没崩(那轮 line 是 None/空,`Evidence(line=None)` 合法)→ e2e #2 line 变成逗号串才崩 —— **LLM 输出方差**,不是稳定复现的代码 bug。
2. 意识到 schema(JSON Schema 声明 `line: integer`)是**契约不是保证**:LLM 偶尔不守(尤其 glm-5.2 给多嫌疑行逗号串),喂进 pydantic 严格模型就崩。

### 根因(为什么是坑)
- **LLM 输出 → pydantic 严格模型** 的边界没做防御:node_report_memorize 盲信 `e.get("line")` 是 int,直接构造 `Evidence`。
- schema 声明不等于 LLM 遵守:DeepSeek/glm 等在结构化产出上有方差(类型不符、多值合并、字段缺失)。pydantic 严格校验 → 单条坏数据崩整个流程。
- 通病:**没核前提**("LLM 会守 schema")—— 同 #1/#2/#3/#4 一脉。

### 教训(可迁移)
1. **LLM 输出喂进 pydantic 严格模型,必加防御 coerce**(int/float/"3067"/"3067,4105"/"3067-3070"/None 全处理,取首个有效值)+ **单条坏不连坐**(try/except 跳过这条,继续)。
2. **schema 是契约不是保证**:delegate(`--format json`)吐的结构化输出,边界处都要当"不可信输入"处理(coerce + 容错 + 降级),不能裸塞严格模型。
3. 这类 bug **e2e 才暴露**(方差性,单测难复现)—— 长尾,逐个 coerce;真要根治得换"LLM 重试到守 schema"或"宽松解析",但成本高,先 coerce 兜底。

### 现状(2026-08-03 定稿)
- `_coerce_evidence_line`(int/float/逗号串/区间串/None 全处理)+ evidence 循环 try/except 跳坏行;单测全 case 过。
- **详见**:`src/hyperion/workflows/bug_rca/nodes.py` `_coerce_evidence_line` + `node_report_memorize`。
